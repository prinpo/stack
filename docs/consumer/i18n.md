# i18n Block

Use General Translation with application-owned dictionaries. Configure one instance per browser application or Bun runtime. The browser and Bun integrations can run independently. A minimal root `gt.config.json` declares the source and target locales.

```json
{
  "defaultLocale": "en",
  "locales": ["pl"],
  "localeRouting": true
}
```

`defaultLocale` is the source and fallback locale. `locales` lists target locales. Omit `localeRouting` for locale-neutral URLs. `stack doctor` reports the default and targets in text and JSON. Doctor inspects configuration offline. It does not execute application code or check that translations are complete.

Create a JSON dictionary for each locale used by the application. Use nested objects and string leaves. Add the source entry first. GT falls back per entry when a target translation is missing and throws when the source ID is unknown. Stack's normal dev and build commands use these files directly. Any translation automation belongs to the application.

## React and TanStack Router

Place browser dictionaries in `src/i18n/client/{locale}.json`. For example, `en.json` could contain `{"settings":{"title":"Settings"}}`. Define the client once in `src/i18n/client.ts`.

```ts
import type { Dictionary } from "@prinpo/stack/i18n";

import { createI18nClient } from "@prinpo/stack/i18n/react";

import config from "../../gt.config.json";
import source from "./client/en.json";

const catalogs = import.meta.glob<Dictionary>("./client/*.json", { import: "default" });
export const i18n = createI18nClient({
  config,
  source,
  loadDictionary: (locale) => catalogs[`./client/${locale}.json`]?.() ?? Promise.resolve({}),
});
```

Spread `i18n.routerOptions()` into the options passed to TanStack's `createRouter`. Keep ordinary unprefixed route definitions and use the normal Stack mounting helper. For a React application without TanStack Router, use the returned `i18n.Provider` with locale-neutral config. Wrap the app in the provider once. Use `i18n.useTranslations()` for typed messages, `i18n.useLocale()` for the current locale, and `i18n.useSetLocale()` to switch. The async setter rejects if loading fails and keeps the current selection. Use `i18n.getLocale` outside React. The provider updates the document's `lang` and `dir`.

Only the source dictionary is imported eagerly. Vite loads the selected target dictionary when needed. Keep server catalogs outside the browser glob. Native GT utilities including `T`, `useGT`, and formatting components are available from `@prinpo/stack/i18n/react`. Supply the optional `loadTranslations` callback if your app provides local GT-format snapshots for inline or JSX translations.

## Locale URLs and discovery

With prefixes enabled, `/pl/settings` determines the locale even if browser settings prefer English. `/settings` resolves to the English URL when English is the default. An unsupported locale prefix reaches the router's not-found view. Use the bare `/` for a language landing page with visible links. Use `i18n.localePath("/about", "pl")` when deliberately linking to another locale. Switching preserves page, query, fragment, and mounted React state. A locale-only URL change stays on the same route and bypasses navigation blockers.

Provide localized titles, descriptions, and self-canonical URLs for public routes. Use real links between versions. To publish alternates, generate `src/public/sitemap.xml` from the public routes your app wants indexed. The generator takes the deployment origin and one map of locale URLs per public page.

```ts
import { createLocalizedSitemap } from "@prinpo/stack/i18n";

const sitemap = createLocalizedSitemap("https://example.com", [
  { en: "/en/about", pl: "/pl/about" },
  { en: "/en", pl: "/pl", "x-default": "/" },
]);
await Bun.write("src/public/sitemap.xml", sitemap);
```

The sitemap omits private routes you leave out. In prefixed mode the SPA still renders page content and metadata in the browser.

## Bun and Elysia

Place backend dictionaries in `src/i18n/server/{locale}.json`. Initialize the server in `src/i18n/server.ts`.

```ts
import { createI18nServer } from "@prinpo/stack/i18n/server";

import config from "../../gt.config.json";
import source from "./server/en.json";

export const i18n = createI18nServer({
  config,
  source,
  loadDictionary: async (locale) => (await import(`./server/${locale}.json`)).default,
});
```

Use `await i18n.getTranslations(locale)` in scripts or workers. In Elysia, register `i18n.elysia({})` on the [shared backend setup](application-patterns.md#shared-backend-setup) for the request-scoped `locale` and typed `t` context values. The backend chooses a supported language from `Accept-Language`, then uses the default when no preference matches.

Supply `getLocale: i18n.getLocale` to the browser's `createApiClient` to forward its current locale. A request may supply its own `Accept-Language` header. When caching locale-dependent response data in TanStack Query, include the locale in the application's query identity or invalidate the affected queries on a switch.

## Localized API errors

Place error text under `errors` in the server dictionary with one object per code. This dictionary describes `ORDER_CONFIRMED`.

```json
{
  "errors": {
    "ORDER_CONFIRMED": {
      "message": "Order already confirmed",
      "why": "An order can only be confirmed once",
      "fix": "Open the existing order"
    }
  }
}
```

`message` is required in the source entry. `why`, `fix`, and `link` are optional. On the shared Elysia setup, register Stack's `logger()` followed by `i18n.elysia({ ORDER_CONFIRMED: 409 })`. The route module uses the same setup plugin.

```ts
export const orders = new Elysia().use(setupPlugin).post("/orders", ({ localizedError }) => {
  return localizedError("ORDER_CONFIRMED", { orderId: "order-123" });
});
```

Eden sees the literal status and error code and the public data type. The public response carries the request-locale text. Evlog records the source text for consistent incident searches. See [structured failures](logger.md#return-a-typed-failure) for the response shape.
