# Auth Block

Design confirmed and implemented. Standards and spec reviews completed; their findings were fixed with regression coverage.

## Settled scope

- Use Better Auth behind a headless Block, preserving native APIs and types while removing repeated integration work.
- Support email/password, magic links, email OTP, social sign-on, organizations, and last login method. Applications explicitly choose what to enable; support does not imply activation.
- Provide Elysia session/user utilities and browser/server organization utilities, including slug lookup and membership validation. Application-specific organization selection, routing, and policies remain application-owned.
- Begin organization conveniences with organizations, memberships, invitations, and static roles. Preserve native plugin access and refine richer conveniences later.
- Applications own auth UI, redirects, and notifications.
- Accept application-supplied email senders while the Email Block is deferred.
- Provide `browserLog` as standard Stack development tooling, available by default without a separate Vite-plugin opt-in. In development it writes to the server console and broadcasts to every connected browser. Keep ordinary console output unchanged. Do not add tab selection, request correlation, or per-recipient delivery infrastructure for this capability.
- Auth always logs development magic links and OTP codes through `browserLog` when those methods are enabled, even when an application or development sender is configured. A sender such as Mailpit is additional delivery, not a replacement for console output. Thin Stack `magicLink` and `emailOTP` adapters retain native options and inferred types, add automatic development logging, and invoke any supplied sender. Native `betterAuth` and client APIs remain intact.
- Delivery helpers provide the same development logging alongside configured senders for email verification, password-reset links, and organization invitations. Applications still explicitly enable each flow.
- Active development integration must be excluded from built applications even when those applications run in development mode. The complete `browserLog` function becomes a no-op there, including server output. Its availability must not block builds. Prefer native Vite/tooling boundaries to custom source rewriting.
- Generate a basic dedicated Drizzle auth schema using Better Auth's generator. Support applications building on and extending it, with SQL migration ownership retained by the Database Block.
- Add `stack auth` schema generation, explicit configuration/schema checks, diagnostics, and secret generation. Keep `stack doctor` offline and structural.
- Keep native `betterAuth`, `createAuthClient`, plugin options, and additional-field inference. Stack helpers remove integration repetition without introducing a second configuration language.
- Elysia utilities provide nullable session/user lookups, request-local session reuse, and outgoing refresh-cookie propagation. Include a required-auth macro returning 401 and injecting typed user/session as an initial convenience; macros are a provisional interface, not the preferred long-term solution. Membership validation remains separate from authentication.
- Bind server helpers once through `createAuthHelpers(auth)` and retain inferred custom fields. Requests or Elysia context provide headers and receive refreshed cookies; do not use a global auth singleton.
- Native Better Auth hooks own browser session and organization state. Add no parallel session cache or mandatory `/auth/me` endpoint initially.
- Convenient slug-based organization lookup authenticates the caller and validates membership before returning organization details. Public organization discovery remains an explicit application feature.
- Required organization helpers return 401 for anonymous callers and the same 404 for unknown slugs and inaccessible organizations. Unexpected infrastructure failures propagate. Offer separate nullable/checking helpers for application-controlled handling. When evlog is enabled for the request, use its existing structured error integration; otherwise fall back to native Elysia `status`. Auth must not require the Logger Block.
- Stack supplies default development integration and `stack dev` coordinates backend wiring. Applications do not declare `authDevDelivery` or separately enable a Vite plugin. Backend-only applications require no Vite or frontend: server console logging works and browser forwarding is a no-op. Built applications cannot activate development delivery through runtime development mode.
- Browser delivery is live and best-effort. Disconnected/reloaded browsers and development-session restarts do not require durable queues or replay. Delayed callbacks may broadcast while the current development channel is available.
- Builds succeed when only development email delivery is configured. Applications are responsible for supplying a production transport; an enabled email flow without one fails production startup with an actionable error.
- Generated auth schema is replaceable output and is not edited directly. Declare auth extensions through native additional fields; keep other application tables and relations outside generated files. Confirm before overwriting existing generated output.
- Recommend `src/server/auth/config.ts` for server auth configuration and `src/server/database/auth.generated.ts` for generated schema, with explicit CLI paths supported. Doctor inspects conventional files without executing configuration. Explicit generation evaluates the selected configuration but requires neither a live database nor production credentials.
- When last-login tracking is enabled, use native browser-cookie behavior by default and retain native database persistence options.
- Extend the existing full-stack example with minimal UI for password login, OTP, magic links, sessions, organizations, and invitations; document social-provider configuration without requiring OAuth credentials to run the example. Organize the example's routes and views by feature. Keep UI application-owned and runnable without email credentials through development console delivery.
- Qualify the initial Auth Block against SQLite through Bun SQL only. Do not provision PostgreSQL or add a PostgreSQL integration check for this milestone. Preserve native database options without claiming qualification of additional combinations.

## Design closure

No product decisions remain open from this interview. The implementation must satisfy the settled scope and qualification gates below.

Public import paths, exact helper signatures, native CLI delegation, transport mechanics, and serializer details remain implementation choices within the settled requirements. A future alternative to Elysia macros is outside this initial implementation.

## Implementation qualification gates

- Detect evlog through the current request's integration capabilities, not global logger initialization. Preserve the existing advertised Elysia status-response/error contract, including cause-free public serialization, and use native status when the request has no logger integration.
- Validate registered auth delivery requirements after application/plugin initialization and before opening the listener. Elysia start hooks alone do not provide a pre-listen boundary with the installed Bun adapter. Imports and schema generation must not perform startup validation.
- Qualify actual first-generation behavior with the generated file absent, no database service, and no production credentials. Avoid eager reads of absent generated tables/relations in schema-generation configuration.
- Use the real Drizzle relations-v2 adapter generator for RC.5 compatibility. Better Auth's `generate --adapter drizzle` fallback emits the removed `relations` API in inspected versions 1.7.0, 1.7.18, and 1.7.21. Verify the eventual pinned version and generated indexes/foreign keys rather than assuming native offline flags select the correct generator. See [generator dispatch](https://github.com/better-auth/better-auth/blob/v1.7.21/packages/cli/src/generators/index.ts) and [fallback generator](https://github.com/better-auth/better-auth/blob/v1.7.21/packages/cli/src/generators/drizzle.ts).
- Qualify environment precedence and static/offline loading: the native auth CLI loader evaluates configuration and loads dotenv files through c12, independently of Bun's dotenv flag. Use its supported [generation API](https://github.com/better-auth/better-auth/blob/v1.7.21/packages/cli/src/api.ts) if necessary to preserve Stack's contract. See [config loader](https://github.com/better-auth/better-auth/blob/v1.7.21/packages/cli/src/utils/get-config.ts).
- Verify thin plugin adapters preserve native inference and options and log development payloads alongside configured senders. Qualify source and built startup, including direct built-entry execution with development mode, before claiming exclusion.

## Development transport research

Investigations compared native development-process wiring, a small separate relay, Vite-hosted delivery, TanStack's console-pipe transform, and first-party server-console forwarding patterns. The chosen product direction is a default explicit browser-logging capability with broadcast delivery, server console output, and automatic auth development logging alongside configured senders. The reports below predate these decisions: optional plugin declarations, recipient isolation, request correlation, and fallback-only delivery are proposals superseded by the settled scope above. Exclusion from built applications independently of runtime mode remains required.

Completed investigations:

- [Upstream console piping](../research/auth-dev-console-upstream.md): TanStack's named console transform is a Vite plugin, broadcasts output, and does not automatically instrument a separately launched Bun process. Next.js uses request-associated React Flight transport. Both are references rather than drop-in private auth delivery.
- [Vite relay](../research/auth-dev-vite-relay.md): recommends a Vite-hosted, individually targeted channel, with browser request correlation and development backend registration. Native Vite hooks cover browser exclusion; backend exclusion requires its own boundary.
- [Backend wiring](../research/auth-dev-backend-wiring.md): local Bun probes verify that external packages retain runtime export-condition selection and initialize before a statement banner. A side-effect guard import ran before other external initializers in the fixture. Proposes preload activation, an inert runtime facade, and an early built-artifact lock; full integration remains unqualified.

The research supports native development-process wiring and an inert runtime facade; the user selected broadcast simplicity over the reports' recipient-targeting proposals. No browser-auth request headers or destination tracking are needed for logging. The chosen built-app guarantee excludes the active integration from browser output and server execution, while allowing development tooling files to remain in the installed Stack package. See [ADR 0021](../adr/0021-broadcast-explicit-development-browser-logs.md).

## Evidence

- Green Wedge uses an Elysia authentication macro, Better Auth's Drizzle relations-v2 adapter, and email OTP. Its client repeats server additional-field declarations, and its generation command names a different schema output from the checked-in schema.
- Old Prinpo selects organizations through URL slugs and validates membership independently of authentication. This motivates reusable slug and membership utilities without prescribing a universal organization selection policy.
- Stack uses Vite for browser builds and externalized Bun server builds. A browser-only transform or runtime `NODE_ENV` check cannot alone establish exclusion of server development delivery from built applications.
- Existing database policy owns migrations and offline doctor behavior; auth must compose with those boundaries.

See [ADR 0020](../adr/0020-use-better-auth-for-the-auth-block.md).

## Implementation evidence

- Pinned Better Auth, its relations-v2 adapter and supported generation API to 1.7.21. Public native reexports, delivery adapters, bound Elysia helpers and URL-scoped client utilities are implemented.
- `tests/auth-sqlite.test.ts` exercises real Bun SQL SQLite signup, session authentication, OTP, magic links and organization membership/slug behavior against the committed generated schema and migration.
- `tests/auth-helpers.test.ts` checks optional evlog behavior, anonymous failures, inferred session data, request reuse and outgoing refresh cookies. `tests/auth.types.ts` checks custom-field and native plugin-option inference.
- `tests/auth-cli.test.ts` checks first offline generation, schema drift, overwrite protection and structural doctor behavior. The generator uses supported `auth/api` with the real relations-v2 adapter and Stack's static snapshot; it does not invoke c12.
- `tests/browser-log-dev.test.ts` qualifies native IPC through actual CLI/Vite+ processes and broadcast to two connections. `tests/browser-log.test.ts` qualifies backend-only output and direct built-entry no-op behavior with development mode and an inherited preload.
- The example has generated auth tables and SQLite migrations, minimal auth/organization screens, and feature-organized routes/views. Production senders are deliberately app-owned and absent from the teaching example.

## Review corrections

- Restrict generated import forwarding to parsed import declarations so native additional-field default strings remain unchanged.
- Validate plugin-composed native options at the registered, asynchronous pre-listen startup boundary; preserve OTP-based verification overrides. Standalone hosts can await the bound helpers' `validate()` method.
- Follow native session changes in the slug hook and immediately hide data for a previous user/session. Share organization-error classification between lookup helpers.
