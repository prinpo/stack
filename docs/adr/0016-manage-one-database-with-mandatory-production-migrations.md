# Manage one database with mandatory production migrations

Add an optional Database Block using Stack-owned exact `drizzle-orm@1.0.0-rc.5` and `drizzle-kit@1.0.0-rc.5` dependencies. Preserve native Drizzle APIs and native `drizzle.config.ts` configuration; developers choose the dialect, runtime driver, and client options. The first version manages one database per application. Applications own any additional databases without Stack orchestration.

Root `drizzle.config.ts` enables the managed database lifecycle without additional registration. Source migrations live in project-root `migrations/`, enforced by Stack-owned `defineConfig` without an application `out` field. Doctor and build inspect that conventional directory without importing or evaluating executable config. Configurable or profile-dependent migration directories and offline config analysis are deferred.

Production startup always applies committed migrations through the pinned native Kit CLI under Bun before accepting traffic. The initial version has no migration-disable option or alternate deployment-job mode. Kit must therefore be available in production, accepting increased dependency/image size for simpler setup and one native migration execution path. Future Docker/image utilities must account for this runtime dependency.

Development never implicitly pushes schemas, generates migrations, or applies migrations; database mutations are explicit developer operations. Offline doctor reports local migration count but resolves no credentials and makes no database connections. Missing or empty migration directories block build and production startup; doctor explains the production-readiness failure and exits nonzero, including a structured finding in JSON. An absent optional Database Block is informational.

Apply production migrations in the shared startup lifecycle after environment validation and before importing application modules or accepting traffic, including direct Bun startup through `startServer` and Stack's frontend-only production server. CLI startup reaches this gate without executing migrations twice. Failure or interruption terminates startup without importing the application or opening its listener; add no automatic retry, repair, rollback command, or schema-push fallback. Applications retain ownership of native runtime clients and their cleanup. Stack owns server signal handling and its Kit subprocess; `startServer` offers an `onStop(status)` callback for application shutdown actions, with native app stop as the default. It logs “Stopping...” in red and handles exit/error status.

Build packages the compiled Drizzle config and complete migration folders, including snapshots, under `dist/database`, and records the capability/artifacts in the successful build manifest. Preserve credential-free builds and runtime credential resolution. Production uses built database artifacts without requiring source config/schema files; Kit and external driver dependencies remain installed runtime dependencies.

Concurrent-start coordination is deferred. The initial Block does not guarantee safe concurrent migration execution by multiple starting instances. This is a documented limitation, not a requirement to implement deployment serialization. Database provisioning/reset, seeding, and baseline enrollment are also deferred to application/native workflows.

Qualify Stack's database integration with SQLite using Bun SQL, including lifecycle and automatic production migrations. PostgreSQL and alternative Drizzle drivers remain selectable without adding a database-server requirement to Stack's test suite. This testing scope does not establish correctness of untested dialects or driver-specific behavior; Stack remains responsible for its own orchestration, packaging, and failure handling. The full-stack example uses file-backed SQLite through Bun SQL and demonstrates notebook/note relations, persistent reads/writes, and application-owned client cleanup through the server callback. Document PostgreSQL/Bun SQL configuration separately without requiring a PostgreSQL service for the example.

This brings database integration deferred by ADRs 0002 and 0010 into scope. Expose native Kit operations through `stack db` with shared profile/environment handling. Native database import paths are a temporary exception recorded in [ADR 0017](0017-retain-native-drizzle-import-paths-initially.md). See the [database milestone](../milestones/0006-database.md) and [RC.5 evidence](../research/drizzle-rc5.md).
