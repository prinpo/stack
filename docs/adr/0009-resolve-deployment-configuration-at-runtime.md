# Resolve deployment configuration at runtime

Add Varlock as an optional environment Block for schema-driven loading, validation, typed access, and public/secret classification. Preserve native Varlock concepts and APIs with minimal integration code; external secret providers remain optional. This accepts Varlock's schema language and loading lifecycle in exchange for flexible configuration resolution beyond typed validation alone, following the dependency ownership and independent Block boundaries in ADRs 0001 and 0002.

Browser and backend builds must succeed without deployment credentials. Credentials are resolved and validated at runtime rather than embedded in build artifacts, allowing the same built artifacts, including a container image, to be used across deployments. Public configuration may be committed and static when its value is intended to be fixed in the artifact; deployment-specific values must remain dynamic. Builds validate the static configuration they need without requiring dynamic values; the concrete mechanism for skipping dynamic resolution while preserving schema metadata remains to be verified.

Static configuration must not depend on dynamic configuration; a value with a dynamic dependency must itself be dynamic. Prefer an early configuration error for this violation if upstream metadata makes a small, reliable check feasible, without committing to a custom dependency analyzer.

Recommend separate browser and backend schema load roots, with selective imports for shared definitions and locally generated typed access. Schemas default to sensitive values, which are dynamic under Varlock's sensitivity-based timing default; public exposure requires an explicit declaration. Public values may be static or explicitly dynamic, independently of whether their source file is committed.

Resolve and validate required runtime configuration at server startup before accepting traffic. Initially use native `varlock run -- bun ...` scripts with Bun's automatic dotenv loading disabled; a custom Stack launcher is unnecessary. Changes, including credential rotation, require an instance restart; live refresh is outside this integration's scope.

The first integration includes public dynamic browser configuration, verified by serving one browser build under two different runtime configurations. Use an opt-in Elysia endpoint under the API namespace, with a configurable path and `Cache-Control: no-store`, to deliver the browser's declared public dynamic values through Varlock's native serialization and hydration helpers. Applications using those values load them before importing and initializing application modules, and show a clear retryable error if loading fails.

The effective client schema must contain only explicitly public values, including imported definitions. Sensitive values, whether static or dynamic, do not belong in the client graph; prefer an early configuration error when this can be enforced reliably. This is a requirement to verify, not a claim of native enforcement already present in Varlock.

Client exposure and static/dynamic classification must be inspectable without resolving runtime values. Reject runtime-dependent classification rather than fetching credentials to discover whether a client entry is permitted. Backend schemas retain native Varlock flexibility, subject to the static-dependency rule for credential-free builds.

Disable Varlock's automatic log/output redaction and response leak detection in the documented integration with `@redact=false` and `@preventLeaks=false`. Applications own the responsibility to avoid logging or returning secrets; Stack adds no Varlock-aware logger drain or redaction layer. This chooses explicit application discipline over automatic output interception given unmeasured performance and compatibility concerns with the existing logging integration. No evlog incompatibility has been demonstrated. Applications may enable these native protections experimentally at their own risk; this milestone does not qualify those opt-ins with evlog.

Stack owns pinned Varlock core and Vite integration dependencies. Optional provider plugins and their authentication configuration belong to consuming applications; Stack does not bundle or qualify every provider combination.

The compatibility gate reproduced loss of dynamic schema metadata during filtered loading and missing browser-entry metadata under Vite+/Rolldown. The user authorized narrowly maintained patches to the pinned upstream packages rather than weakening the contract or introducing a replacement plugin. Keep their regression checks and document root patch installation requirements: patched dependency manifests do not apply transitively, and independently installed package qualification remains deferred under ADR 0004.
