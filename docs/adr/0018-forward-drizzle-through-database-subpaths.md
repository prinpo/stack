# Forward Drizzle through database subpaths

Expose Drizzle's root API through `@prinpo/stack/database`, alongside Stack-owned `defineConfig`, and mirror its ORM subpaths under `@prinpo/stack/database/...`. This supersedes ADR 0017's temporary native-import exception and restores the dependency/reexport policy of ADRs 0001 and 0002. Preserve native symbols and types; keep dialects, drivers, migrators, and validators in separate entry points so importing common helpers does not initialize every optional runtime.

Generate thin JavaScript and declaration forwarding modules from the pinned ORM's published wildcard export surface during repository preparation and release packaging. Keep generated files out of source control, verify them through the generation script's check mode, and ship them in the tarball so consumers need no generation scripts. Generate both named and any default reexports without copying the ORM implementation. A changed upstream export layout must fail generation rather than silently publish an incomplete surface. External drivers and validator peers remain required only when their corresponding native entry points require them.

Expose the built-in `drizzle-orm/zod` utilities through `@prinpo/stack/database/zod` as an optional integration using Stack's existing pinned Zod dependency. Demonstrate a derived/refined/picked insert schema on the example notebook endpoint while retaining Elysia TypeBox schemas elsewhere. Table-derived validation does not replace application rules or field selection, and importing the database root does not import Zod validation.

The example browser artifacts remain unchanged after forwarding and the Zod demonstration. A browser bundle using SQL helpers is the same size through direct or Stack imports. The externalized server entry grows only by import-path and example-validation code; no new dependency is added. See the database milestone for measured build sizes and installed-consumer qualification.
