# Derive job clients from BullMQ job definitions

Build the Jobs Block on BullMQ with Redis as the initial datastore. Define each job's input schema alongside its handler, infer its result from the handler, and derive the producer API from those definitions rather than maintaining parallel producer and worker contracts. Producers initially run in backend code and connect directly to Redis; submitting work does not require an HTTP jobs service.

Validate inputs before accepting submitted work and at the worker boundary because queued data can outlive a deployment or arrive from another producer. Accept Standard Schema validators, with Stack's existing Zod dependency as the preferred validator. Invalid worker inputs and unknown job names are unrecoverable job failures, while ordinary handler failures retain configurable BullMQ retry behavior.

Keep native JSON serialization initially, accepting the loss of rich values such as Date instances in transported results rather than adding a serialization protocol. Mapping inferred result types to their JSON representation is explicitly deferred; document this limitation. The initial typed surface covers named enqueueing, handlers, retrieval, completion results, and progress. Bulk submission, scheduler helpers, and the typed flow API are deferred until application usage informs their design.

Register runtime queue definitions once during startup and expose a lightweight producer client inferred from their types. Validate the serialized input before enqueueing but store that input unchanged, discarding the validator's transformed output. At the worker boundary, validate the stored input again and pass the transformed output to the handler. Support asynchronous validators; validation and transformations should be free of side effects because submission and execution each validate independently.

Progress always has the shape `{ phase: string, percent: number }`, initially `{ phase: "processing", percent: 0 }`. A job may declare a nonempty list of custom phases inferred as a literal union. Custom phases are required on progress updates when declared; otherwise callers may omit the phase and receive the default. Reading progress must account for the initial "processing" phase even when updates require a custom phase. Validate updates at runtime, require percent in the inclusive range 0–100, allow decimals, and do not enforce monotonic progress.

Define jobs individually with their schemas and handlers, then compose them into explicitly named queues with shared worker options. Recommend a dedicated jobs directory and an explicit composition entry rather than filesystem discovery. Definition helpers must not open connections or start workers.

Preserve `jobs.<queue>.add.<job>(input, options?)` for enqueueing. Native job options take precedence from queue defaults to job defaults to per-enqueue overrides, with native BullMQ defaults when unspecified; applications own retry, backoff, deduplication, and retention policy. Use `jobs.<queue>.run.<job>(input, { timeoutMs, job? })` to enqueue and await the completed result, with a required finite timeout and separate native job options. It rejects on terminal failure or timeout; timing out ends the wait without cancelling the job, and retries remain within the waiting period.

Queue-wide `jobs.<queue>.getJob(id)` retrieval returns a discriminated job union narrowed by the actual job name, or `undefined` for a missing job. Also provide `jobs.<queue>.getJob.<job>(id)` for checked retrieval returning that job's type, or `undefined` when missing or of another job kind. For matching jobs, validate and transform stored input before exposing data, giving callers the handler's data shape; malformed matching data rejects with a validation error.

Retain these decisions for the deferred flow API: preserve BullMQ's child-before-parent semantics; let parents reference existing job definitions through an optional `children` list to declare allowed child kinds without repeating result types; validate relationships on submission; infer child-result values as the union of the declared children's results in BullMQ's job-keyed map. Default to propagating terminal child failure through `failParentOnFailure`, with native alternatives available explicitly. This deliberately differs from BullMQ's default of leaving failed dependencies unresolved; parent failure is finalized by a parent worker and does not cancel siblings. Flow submission syntax, exact cardinality, and named result slots remain deferred, and these future contracts are not part of the first implementation.

Initially run workers in the backend process; a separate worker-process lifecycle is deferred. Use Stack's existing development Compose lifecycle for local Redis and let Stack own connection setup, readiness, and cleanup through an optional integration. Development Compose waits for Redis readiness, and configured jobs must be ready before the application accepts HTTP traffic. Bound producer waits during Redis outages while retaining worker reconnection behavior.

Applications own datastore environment settings and supply the native BullMQ connection configuration; Stack does not own a Redis URL or require one datastore through its configuration API. Redis remains the initial example infrastructure. Register jobs through an optional Elysia plugin composed into the application's shared `setupPlugin` alongside logging and auth. Reuse that named setup instance on the root app and route modules, following the shared backend setup pattern in the consumer documentation.

Support a bounded graceful shutdown through the Stack-owned `JOBS_SHUTDOWN_TIMEOUT_MS` environment variable, defaulting to `30000`; validate nonnegative integers, with `0` selecting immediate shutdown. Development and production can select different grace periods through the existing environment profiles. Managed termination must respect the grace period; development reload behavior must be verified and documented. Keep independently usable jobs APIs in keeping with ADR 0002.
