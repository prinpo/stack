# Allow explicit Stack lifecycle configuration

Conventional file discovery is useful when Stack owns an application's lifecycle. An application can also have operator tools and shared infrastructure whose lifetimes differ from a Stack command. Allow an optional root `stack.config.ts` so the application can declare that policy explicitly. The absence of the file or an individual override retains the existing default. This revises the convention-only decision in [ADR 0010](0010-own-application-commands-through-the-stack-cli.md).

Applications default-export `defineConfig({...})` from `@prinpo/stack/config`, which returns a typed, JSON-compatible object. The top-level options are `compose` keyed by command, `database` for database ownership, and `scripts` keyed by command and phase. One Zod schema defines the type and validates source configuration and the policy stored in the build manifest. `stack doctor` uses the same validation, flags unknown options and missing script names, and reports effective behavior and its source. For example, it can distinguish a Compose file disabled by configuration from a missing file.

Development and preview each choose a Compose policy. `managed` is the default and retains conventional discovery, readiness checking, and shutdown. `start-only` starts Compose and waits for readiness, then leaves it running when the session ends. After a partial startup, managed attempts to stop the project and start-only leaves it available for inspection. Both hold the project lock for the session. `external` leaves Compose to the application developer. This extends [ADR 0015](0015-manage-development-compose-through-stack-dev.md).

An application can own its database lifecycle even when root `drizzle.config.ts` is present. In this case Stack skips automatic migration checks, packaging, and execution in its application lifecycle. Explicit database commands are still available. The managed default retains the checks and migrations in [ADR 0016](0016-manage-one-database-with-mandatory-production-migrations.md).

Applications opt into lifecycle scripts by registering one `package.json` script name per command phase. Scripts inherit the command's environment and profile and can invoke Varlock explicitly. Dev and preview run `pre` after Compose readiness and `post` after application shutdown, while Compose dependencies are still available. The pair runs once per session. Failed `pre` blocks app startup, and `post` can clean up partial work. An orderly interrupt follows the same cleanup sequence. Compose startup failure skips both. If `post` fails, Stack still attempts Compose teardown and preserves an earlier failure or signal status.

Build runs `pre` before building and `post` after the artifacts are ready. Stack publishes the manifest only after the build and its scripts succeed. Production `stack start` and ordinary `stack worker` can each run `pre` from the manifest before handing off directly to the runtime. A failed script blocks handoff. Worker readiness checks remain side-effect-free with respect to lifecycle scripts. Preview runs its own lifecycle scripts. Application shutdown runs in the runtime, and the deployment supervisor owns actions that run after the process exits.

`stack build` captures the resolved policy needed by the built application. A built production launch reads the policy from the manifest, including when Bun runs the built entry directly. When Bun runs a source entry directly in production mode, `startServer` reads the database ownership policy from the application's `stack.config.ts`. Both paths honor `database: "external"`. Registered lifecycle scripts run through the corresponding Stack CLI command.

The manifest changes from version 2 to version 3 and requires rebuilding existing artifacts. Dev and preview read local session settings when the command starts. Deployment values remain in [Varlock](0009-resolve-deployment-configuration-at-runtime.md), and application developers own production image construction.
