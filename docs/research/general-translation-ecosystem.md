# General Translation CLI, catalogs, and runtime compatibility

Research date 2026-11-20. The i18n Block's current decisions are application-owned JSON catalogs, browser loading by active locale, and server-side localization by error code. This note checks which upstream GT paths fit that model. [ADR 0025](../adr/0025-load-browser-translations-by-active-locale.md) · [ADR 0026](../adr/0026-localize-public-api-errors-by-code.md) · [ADR 0027](../adr/0027-use-general-translation-for-i18n.md)

## Two catalog formats

| Format                                         | Identity and contents                                                                                                                                                                              | How it is consumed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application dictionary or generic `files.json` | Application-defined string IDs such as `errors.orderConfirmed.message`, with nested objects or flat string entries as appropriate. A generic JSON file can be translated independently of any SDK. | Use `dictionary` or the provider's dictionary snapshot for source data, and `loadDictionary(locale)` or a target dictionary snapshot for target data. Resolve by ID with React `useTranslations` or Node `getTranslations`. [JSON format](https://generaltranslation.com/en-US/docs/cli/reference/formats/json-files) · [React dictionary loader](https://generaltranslation.com/en-US/docs/react/reference/functions/load-dictionary) · [Node config](https://generaltranslation.com/en-US/docs/node/reference/config#dictionary)                                                                                                                                                                                               |
| `files.gt.output` or GTJSON                    | Flat `hash → translation` per locale. Values can be strings or serialized JSX. `generate` creates one file per locale at the output pattern.                                                       | `loadTranslations(locale)` supplies the per-locale map. For React's provider, `translations` has the outer locale key, as in `getTranslationsSnapshot(locale)`. These inputs support native inline translation and can also supply the translation of a source dictionary entry by its content hash. [GT file format](https://generaltranslation.com/en-US/docs/cli/reference/formats/gt-jsx-files) · [Snapshot helper](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/react-core/src/functions/helpers/getTranslationsSnapshot.ts#L10-L28) · [Dictionary resolution](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/i18n/src/translation-functions/internal/getTranslations.ts#L73-L93) |

For the current Stack catalogs, a possible hosted file configuration is `files.json.include: ["src/i18n/client/[locale].json", "src/i18n/server/[locale].json"]` with only the paths the application uses. The CLI substitutes the default locale to find the input and the target locale to choose the output path. File-based automation can therefore return the same semantic-key structure the i18n Block already reads. A `dictionary` setting instead picks one source dictionary for SDK extraction. Its entries become hashes in the generated snapshot. Use distinct paths for GTJSON artifacts and application dictionaries if both are present. [CLI file configuration](https://generaltranslation.com/en-US/docs/cli/reference/config#files) · [Dictionary option](https://generaltranslation.com/en-US/docs/cli/reference/config#dictionary) · [Dictionary extraction](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/react/parse/createDictionaryUpdates.ts#L65-L115)

### Explicit IDs

A dictionary ID is the lookup key and can remain stable when copy changes. GT resolves the source entry by that ID, then prefers the target dictionary entry by ID, tries any loaded translation for the source content hash, and otherwise renders source text. A missing source ID is a lookup error in the tested Node keyed resolver. [React dictionary guide](https://generaltranslation.com/en-US/docs/react/guides/translating-with-dictionaries) · [Node lookup](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/i18n/src/translation-functions/internal/getTranslations.ts#L73-L93)

Inline `id` on `<T>` and `$id` in string options such as `gt("Text", { $id: "page.title" })` or `msg("Text", { $id: "page.title" })` identify entries for tooling and the translation editor. Prefer `<T id="page.title">`. Both JSX spellings work at these pins, and CLI 2.28.4 warns on the older JSX `$id` even though the public component reference still lists it. The CLI rejects a repeated ID when its entries have different hashes. Runtime lookup hashes the content and format plus applicable context, character limit, or review metadata. Changing only the inline ID leaves the hash intact. Changing the source wording can make the previous translation a stale hash even if the ID stays fixed. `msg([...], { $id })` appends `.<index>` to the ID of each entry. [String options](https://generaltranslation.com/en-US/docs/react/reference/types/inline-translation-options#id) · [Node msg options](https://generaltranslation.com/en-US/docs/node/reference/functions/msg#options) · [JSX prop parser](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/react/jsx/utils/jsxParsing/parseTProps.ts#L19-L108) · [Duplicate ID validation](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/translation/parse.ts#L104-L169) · [Runtime hash](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/i18n/src/utils/hashMessage.ts#L10-L36)

## Local extraction, build compilation, and hosted translation

- **Local extraction.** `gt validate` scans the SDK source and dictionary. `gt generate` scans and writes GTJSON templates through `files.gt.output`. It replaces the source template, preserves target values for hashes still present, seeds new hashes from source, and prunes obsolete hashes. It leaves generic `files.json` targets alone. `generate --dry-run` still writes templates. For a nonstandard dictionary path, pass `--dictionary <path>` explicitly with `generate` in 2.28.4. The scanner used by generation reads the flag or falls back to conventional dictionary filenames, while `validate` uses the merged config setting. This differs from the generation docs. The same aggregator is called by hosted file collection. [Generate docs](https://generaltranslation.com/en-US/docs/cli/reference/commands/generate) · [Template writer](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/cli/inline.ts#L119-L178) · [Dictionary resolution in aggregation](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/translation/stage.ts#L11-L37) · [Validation](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/translation/validate.ts#L53-L80) · [Hosted collection](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/formats/files/collectFiles.ts#L43-L61)
- **Framework detection matters.** The CLI reads `package.json` in the working directory, looking at direct dependencies and dev dependencies. A consumer whose manifest declares only Stack selects the base CLI, which lacks `generate` and `validate`. If the same package declares `gt-react` and `gt-node`, React wins and the selected parser excludes direct Node imports. The parser also filters imports by recognized GT package prefixes, so native calls and components imported through Stack's re-exports were invisible in a fixture. Changing the source glob or the config path alone does not change the selected parser. Separate manifest/source roots can select each SDK adapter if a future application needs native extraction on both sides. [Framework detection](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/fs/determineFramework/index.ts#L26-L69) · [Allowed imports by SDK](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/types/libraries.ts#L92-L125) · [Import scan](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/react/jsx/utils/getPathsAndAliases.ts#L75-L109)
- **Build compilation.** CLI 2.28.4 exposes neither an `extract` nor a `compile` command. The optional `@generaltranslation/compiler` is a separate build plugin for Vite, webpack, Rollup, Rspack, or esbuild. It can transform JSX and inject precomputed hashes and lookup metadata. Automatic JSX insertion requires its parsing flag in the common GT config to align the plugin with the CLI's simulated insertion. The compiler's recognized GT import sources omit `gt-node`. The simple Node and React inline cases below translated without running this plugin. [Compiler exports](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/compiler/src/index.ts#L216-L334) · [Compiler import sources](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/compiler/src/utils/constants/gt/constants.ts#L95-L105) · [Automatic JSX guide](https://generaltranslation.com/en-US/docs/cli/guides/using-auto-jsx)
- **Hosted translation and local delivery are independent.** `gt translate` uses the project ID and an authorized login or tooling key. It collects files, uploads source material, queues translations, and downloads results. The split commands include `upload`, `enqueue`, `stage`, and `download`. The `save-local` command sends local edits back to GT. A local output and a runtime loader can remove the runtime CDN dependency while generation still runs on GT's service. `publish` controls CDN publication. The docs describe `translate --dry-run` as local parsing and validation, but 2.28.4's normal stage path invokes the review warning before its dry-run return, and that warning can attempt a project-info read for review-gated files. `validate` and `generate` are the relevant commands when excluding all contact with a GT project. [Translate docs](https://generaltranslation.com/en-US/docs/cli/reference/commands/translate) · [Local delivery](https://generaltranslation.com/en-US/docs/react/guides/storing-translations) · [Dry-run ordering](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/cli/commands/stage.ts#L34-L58) · [Project-info check](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/src/translation/reviewSetupWarning.ts#L23-L51)

## Verification

### Tested

Temporary synthetic fixtures used Bun 1.4.4, Node 26.13.0 for comparison, and the package pins above. The React runtime smoke test used Stack's React and React DOM pin, 19.3.1. CLI and runtime probes ran with a cleared credential environment, an isolated home, and a local preload that rejected `fetch`. No GT project, credentials, or application content were used.

- `bun --bun gt --help`, `bun --bun gt generate --help`, `bun --bun gtx-cli --version`, and `bun --bun gtx-cli validate` worked. Both packages ship Node shebangs. Bun as an installer and Bun as the forced CLI runtime are distinct choices. `node ./node_modules/gt/bin/main.js validate` also passed in the same mixed fixture. [CLI launcher](https://github.com/generaltranslation/gt/blob/gt%402.28.4/packages/cli/bin/main.js) · [Node SDK quickstart and Bun package installation](https://generaltranslation.com/en-US/docs/node/quickstart)
- `bun --bun gt validate` and `bun --bun gt generate` selected React in the mixed fixture and extracted `<T>`, `useGT`, and `msg`, while omitting the direct Node calls. Running the CLI from a separate fixture declaring just `gt-node` extracted `getGT` and `msg`. Replacing the recognized React import with Stack's re-export path reduced the mixed validation count to the dictionary entry alone. A manifest declaring only Stack exposed base help without `generate` or `validate`. Duplicating an inline ID with different text made validation exit 1.
- `bun --bun gt generate --dictionary src/catalogs/en.json --dry-run` wrote the source and target GTJSON files. It included the dictionary that a config-only dictionary path omitted from generation. Subsequent runs preserved a manually translated target when only the inline ID changed, pruned a stale hash, and inserted source text under the new hash after a wording edit. The generic JSON target was never created by these generation runs.
- In a Bun process, `gt-node` loaded hashed fixtures and application dictionaries locally. Concurrent `withGT` scopes kept their respective locales across awaits. Inline `getGT` and `getMessages` resolved the hashed entries. Keyed `getTranslations` resolved target text, interpolated variables, fell back to source text, and threw for a missing source ID. Upstream documents Node 18+ and uses `node:async_hooks`. The fixture verifies these runtime paths under Stack's Bun version. - Bun rendered matching React HTML with the regular `gt-react` server entry, `react-dom/server`, a local hashed loader, `getTranslationsSnapshot`, and `GTProvider`. The fixture resolved `<T>` with nested markup, `useGT`, `msg` with `useMessages`, and a keyed provider dictionary. Synchronous SSR used the target `dictionaries` provider snapshot for keyed rendering. ## Stack integration findings

Stack pins `gt-react@11.4.24`, `gt-node@1.0.46`, and `generaltranslation@9.5.13`. React runs one controlled GT provider. It loads the source dictionary and only the selected target dictionary, optionally adds a per-locale snapshot from the app's `loadTranslations` callback, and preserves component state during switches. Bun initializes `gt-node`, resolves `Accept-Language` for each request, and uses GT's request-scoped dictionary lookup. Stack wraps that lookup to infer keys from the source JSON and map localized error copy onto stable Elysia statuses, Eden error codes, and evlog source-language records. Both runtimes pass `cacheUrl: null` and `runtimeUrl: null`. Doctor reads the locale fields offline. Stack currently exposes no GT CLI executable or compiler plugin. ### What an application can use today

Point GT's ordinary JSON pipeline at the existing dictionaries. This keeps keys such as `settings.title` and `errors.ORDER_CONFIRMED.message` in the same JSON structure and lets translations generated by GT, another tool, or a human use the current `loadDictionary` functions.

```json
{
  "defaultLocale": "en",
  "locales": ["pl"],
  "localeRouting": true,
  "files": {
    "json": {
      "include": ["src/i18n/{client,server}/[locale].json"]
    }
  }
}
```

```sh
bun add -d --exact gt@2.28.4
bun --bun gt translate --dry-run
```

The dry run found both source catalogs in the synthetic fixture and reported sending no files. An actual `bun --bun gt translate` is an app-owned hosted operation requiring a project ID and a saved login or suitable tooling key. Keep the generated result in Git or provide another app-owned loader. In the fixture, native `gt init --no-interactive --defaults --no-react-setup --no-dev-credentials --no-locadex` kept the locale fields and added the schema, but also wrote a separate local loader. Editing the existing config keeps the Stack setup simple. Use precise file globs because the translation service receives the matched source content, including any server error strings. Keep machine-readable values and URLs that must stay verbatim out of automatic translation inputs, or verify their treatment using the file-format controls. GT also supports per-key context files for JSON. [GT config](https://generaltranslation.com/docs/cli/reference/config#files) · [Translate command](https://generaltranslation.com/docs/cli/reference/commands/translate) · [Keyed metadata](https://generaltranslation.com/en-US/blog/gtx-cli_v2_10_0)

For inline React, use an exact, matching direct app dependency on `gt-react` for the current extractor and import scanned symbols from `gt-react`. Keep Stack's provider and locale hooks. Configure `files.gt.output`, for example `src/i18n/gt-client/[locale].json`, and provide a lazy `loadTranslations` callback over that directory. Render `<T id="settings.title">Settings</T>` or `useGT()("Save changes", { $id: "settings.save" })` under the provider. For reusable declared messages, use `msg` with `useMessages`. Use `gt generate` for local templates and `gt validate` to check the inline scan. For hosted translations, use `gt translate` explicitly. [Vite SPA setup](https://generaltranslation.com/docs/react/guides/spa/configuring-vite-spa) · [Message declarations](https://generaltranslation.com/docs/react/reference/functions/msg) · [Translation loader](https://generaltranslation.com/docs/react/reference/functions/load-translations)

### Verified integration gaps

- **Re-export and project detection.** With both a native-import React file and a Stack-import React file, `gt validate` found only the native entries. The public Vite compiler hook transformed the native `useGT` call and returned null for the Stack-import file. [Framework detection](https://github.com/generaltranslation/gt/blob/016a53ca61f9ba350cbd16533de8648e192e4077/packages/cli/src/fs/determineFramework/index.ts) · [Compiler package constants](https://github.com/generaltranslation/gt/blob/016a53ca61f9ba350cbd16533de8648e192e4077/packages/compiler/src/utils/constants/gt/constants.ts)
- **Inline runtime.** In a Bun and Happy DOM fixture the current Stack React provider rendered a synthetic Polish GT snapshot for both `<T id=...>` and an inline `useGT` string, alongside a keyed dictionary value. A second run supplied an empty target dictionary and resolved the keyed value through the same snapshot by source hash. The render fixtures blocked network access. In the CLI fixture, changing only the React IDs left the output hashes unchanged. Editing the source text changed its hash. Use inline IDs for editorial identity and keyed JSON when application code needs to resolve a durable ID without passing source text. Stack's Bun adapter has no corresponding snapshot-loader option. In an isolated Bun process, the upstream initializer consumed a synthetic Polish snapshot under `withGT` for both `getGT` and `getMessages` using CLI-generated keys. [GT generate implementation](https://github.com/generaltranslation/gt/blob/016a53ca61f9ba350cbd16533de8648e192e4077/packages/cli/src/cli/inline.ts) · [Node initializer](https://github.com/generaltranslation/gt/blob/016a53ca61f9ba350cbd16533de8648e192e4077/packages/node/src/setup/initializeGT.ts)
- **Config and editor integration.** Stack passes canonicalized locale tags to loaders. The CLI fixture generated `fr-ca.json` when the config listed `fr-ca`, while an exact Stack loader would look for `fr-CA.json`. Use canonical spelling today. A future resolver should preserve configured file tags while keeping canonical tags for negotiation and routing. GT's `customMapping`, project/version metadata, CDN config, and runtime options are not forwarded. The shipped guide imports the root config in browser code, so any more expressive runtime integration should expose only the intended public fields. [CLI locale spelling and aliases](https://generaltranslation.com/docs/cli/reference/config) · [Stack locale parser](../../src/i18n/config.ts)
- **Bootstrap and hot reload.** Stack initializes in a React effect. Native module-level `t()` needs translations before application modules evaluate, and values computed at import time do not react to in-place switches. Use render-time `T`, `useGT`, and `useMessages` first. An isolated production build composed Stack's Vite preset with `@generaltranslation/compiler@1.3.70` using direct native imports. Its manifest listed the locale snapshots as dynamic imports. Module-level macros and hosted development hot reload still need separate qualification with explicit credential configuration and checks on production output. [Native Vite bootstrap](https://generaltranslation.com/docs/react/guides/spa/configuring-vite-spa) · [Module-level translation](https://generaltranslation.com/en-US/blog/gt-react_v10_12_0) · [Compiler and development hot reload](https://generaltranslation.com/en-US/blog/gt-react_v10_19_0)

## Recommended implementation order

1. **Document and qualify the native CLI with the existing JSON path.** Provide a copyable config and a local fixture. Keep `gt` available as an optional pinned tool and retain its native commands and flags. A Stack check can add value by checking source/target file coverage, source keys and placeholders, and version compatibility. Report completeness separately so GT's per-entry fallback stays useful. Continue to keep Doctor structural. Keep accounts, jobs, uploads and publishing user-triggered. [Stack library ownership](../adr/0001-stack-owns-library-dependencies.md) · [GT CLI credentials](https://generaltranslation.com/docs/cli/guides/configuring#credentials)
2. **Make inline GT first-class alongside dictionaries.** Add the Bun snapshot loader and a request-bound inline translator. Expose upstream authoring helpers such as `useMessages` and `getMessages` and preserve native capabilities like dictionary subtree access when adding typed wrappers. Add an opt-in Vite compiler with matching CLI config, and a browser composition that can run with only snapshots when no keyed dictionary is needed. Work with GT upstream for configurable import sources and explicit framework selection, so Stack re-exports and a full-stack manifest are recognized. Until that exists, document exact-version direct native imports for scanned files and keep browser and Bun extraction in separate package roots when both are used. Test nonzero expected extraction counts to catch silent skips. [Stack native API policy](../adr/0002-compose-independent-blocks-with-native-apis.md) · [Compiler](https://generaltranslation.com/en-US/blog/compiler_v1_0_0_gt-next_v6_7_0)
3. **Offer hosted workflows as explicit extensions.** Start with native CLI staging, downloads, local edits, and branch review. Let an app choose committed outputs, its own CDN loader, or GT CDN delivery with project/version pinning and a local fallback policy. Treat browser dev hot reload and server runtime translation as separate opt-ins with matching credentials and production exclusions. If Stack later enables any hosted path automatically, reopen ADR 0027 because it currently assigns automation to the application. [Staging and version config](https://generaltranslation.com/docs/cli/reference/config#stage) · [Save local edits](https://generaltranslation.com/docs/cli/reference/commands/save-local) · [GT GitHub Action](https://github.com/generaltranslation/translate)

Acceptance should cover a frontend-only fixture, a Bun-only fixture, and a mixed example. Check that each authoring mode discovers the intended entries, that the example switches locale without remounting, that one target snapshot loads at a time, that no backend content is published in client assets, and that standard Stack build and runtime work offline with the resulting artifacts. Hosted translation, publishing, credentials, and development hot reload were researched against documentation and upstream code. They were not exercised against a real GT project.
