# Varlock inspection for Stack

This opening section records the original research snapshot. Later sections record executed probes; the implemented behavior and patch requirements are in [the environment guide](../env.md).

Inspected on **2026-10-28** against official documentation, npm registry metadata, and upstream source. Varlock's current published version is **1.23.0**; `@varlock/vite-integration` is **1.5.4**. Both release tags resolve to **`1b7fa9a4daa5eae432e6e3daa37a76cbb0089940`**. Source links below are pinned to that release unless explicitly marked otherwise. The temporary inspection checkout is `/tmp/stack-varlock-research`. This is research, not an architecture decision or a tested integration. No dependencies were installed and no application code was changed. ([Varlock registry](https://registry.npmjs.org/varlock), [Vite integration registry](https://registry.npmjs.org/@varlock/vite-integration), [Varlock tag](https://github.com/dmno-dev/varlock/releases/tag/varlock%401.23.0), [integration tag](https://github.com/dmno-dev/varlock/releases/tag/%40varlock%2Fvite-integration%401.5.4).)

## Assessment for Stack

Varlock is a credible candidate when Stack wants a shared, executable configuration specification plus secret resolution and exposure guardrails. Its cost is a schema language, generated types, CLI lifecycle, and runtime patches beyond ordinary environment validation. T3 Env remains a strong, smaller candidate when the requirement is a typed application configuration object over values already loaded by Bun/Vite. Neither choice follows automatically from the current ADRs.

Relevant repository constraints and observations:

- [ADR 0001](../adr/0001-stack-owns-library-dependencies.md) makes Stack own exact versions and upgrades of integrated dependencies. A Varlock block would therefore bring ongoing ownership of the core package and any bundled integration/provider plugins. Applications still own their configuration values and credentials. Installing every available provider is not implied by this ADR.
- [ADR 0002](../adr/0002-compose-independent-blocks-with-native-apis.md) favors independent blocks and native upstream APIs. Environment integration was deferred there. A future block must work without Elysia, React, or the router where upstream permits. Automatically loading application configuration merely by importing unrelated Stack entry points would introduce an artificial prerequisite. These are design implications, not an approved export design.
- [ADR 0003](../adr/0003-vite-plus-and-bun-with-a-single-public-origin.md) and [the example scripts](../../examples/fullstack/package.json) use separate Vite+ and Bun processes. The Vite plugin cannot initialize the separately launched backend. Conversely, wrapping a backend command does not supply browser build replacements. Separate deployments remain supported, and public browser configuration may need to differ from backend configuration.
- [The current Vite block](../../src/vite.ts) returns native Vite plugins for routing, React, and optional proxying. [The example config](../../examples/fullstack/vite.config.ts) uses Vite+ and `--configLoader runner`; the root [manifest](../../package.json) aliases Vite to Vite+ core. Varlock's ordinary Vite API is a plausible extension point, but compatibility with this exact Vite+ alias/config runner/plugin combination remains untested.
- [The server entry](../../examples/fullstack/src/server/index.ts) selects production serving via `NODE_ENV`; [logging setup](../../examples/fullstack/src/server/logging.ts) uses `PRINPO_LOG_DIR`. Introducing a separate environment selector must preserve the meaning of `NODE_ENV`. [ADR 0004](../adr/0004-develop-examples-against-stack-source.md) makes source-linked development the active workflow; a research spike need not reopen distribution/build decisions.

## Schema, loading, validation, and types

`.env.schema` is a shareable configuration schema with defaults, descriptions, and `@env-spec` decorators. Decorators are structured comments, not TypeScript decorators. Root decorators belong in the file header; item decorators attach directly to an item, with a divider separating the header. Resolver calls extend ordinary dotenv value syntax, so the schema must be interpreted by Varlock to obtain those semantics. ([Schema guide](https://varlock.dev/guides/schema/), [pinned schema documentation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/schema.mdx), [language reference](https://varlock.dev/env-spec/reference/).)

Illustrative schema only, not a proposed Stack convention:

```dotenv
# @currentEnv=$APP_ENV
# @defaultRequired=true @defaultSensitive=true
# @generateTsTypes(path=./env.d.ts)
# ---

# @sensitive=false @type=enum(development, test, production)
APP_ENV=development

# @sensitive=false @type=number(min=1, max=65535, isInt=true)
PORT=3000

# @sensitive=false @type=url
PUBLIC_API_ORIGIN=http://localhost:5173

# @sensitive @type=string(minLength=16)
API_TOKEN=
```

`@required`/`@optional` govern presence, `@type` coercion and validation, and `@sensitive` exposure metadata. Built-in defaults without decorators are required and sensitive; **`varlock init` instead writes `@defaultRequired=infer` and `@defaultSensitive=false`**. Generated schemas therefore need review: omission of `@sensitive` can make a newly added credential public under the initializer's defaults. These defaults apply within their file, rather than automatically carrying into imports or override files. ([Root decorators](https://varlock.dev/reference/root-decorators/), [pinned reference](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/reference/root-decorators.mdx).)

Loading precedence, from lowest to highest, is `.env.schema`, `.env`, `.env.local`, `.env.[currentEnv]`, `.env.[currentEnv].local`, then ambient process overrides. `@currentEnv=$APP_ENV` selects the environment independently of Vite's mode and overrides CLI `--env`. Varlock recommends avoiding `NODE_ENV` as that selector. `KEY=` means undefined and does not clear a lower-precedence value; `KEY=""` explicitly overrides with an empty string. This is a migration difference from assuming every dotenv assignment is an opaque string. ([Environments guide](https://varlock.dev/guides/environments/), [pinned environment documentation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/environments.mdx), [schema guide](https://varlock.dev/guides/schema/).)

Resolution precedes coercion and validation. Types include string, number, boolean, URL, enum, arrays, and objects; options constrain or transform values. Boolean conversion explicitly recognizes true/false spellings such as `yes`/`no`, `on`/`off`, and `1`/`0`, rejecting other values. Numeric precision options can round before validating, so coercion policy deserves review rather than assuming rejection of every noninteger input. Inferred types depend on quoting; explicit types remove ambiguity. In 1.23.0 some stricter URL checks warn rather than fail until the next major, so `@type=url` alone should not be described as rejecting every malformed URL today. ([Data types](https://varlock.dev/reference/data-types/), [pinned type documentation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/reference/data-types.mdx), [1.23.0 changelog](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/CHANGELOG.md).)

`@generateTsTypes` generates declarations for `import { ENV } from 'varlock/env'` and configurable `process.env`/`import.meta.env` augmentation. `ENV` exposes coerced values, including numbers and booleans; native process environment access remains a string boundary. Generation occurs during `load`/`run` or explicitly via `codegen`, and derives from environment-independent schema information. `exposeEnv=local` supports package-local typing to avoid global augmentation collisions across different application schemas. A Stack reexport must preserve this upstream declaration mechanism; that has not been tested. Generated declarations alone do not load or validate anything. ([Code generation](https://varlock.dev/guides/code-generation/), [pinned generation guide](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/code-generation.mdx), [monorepos](https://varlock.dev/guides/monorepos/).)

## Vite+, Bun, and separate frontend/backend execution

The documented frontend integration is `varlockVitePlugin()` from `@varlock/vite-integration`, listed before other plugins. It loads/validates configuration, replaces static `ENV.KEY` accesses, supports `%ENV.KEY%` HTML replacements, and watches loaded files through Vite's configuration dependencies. Invalid configuration blocks builds; dev mode presents an error page and can recover after correction. It supports configuration-time `ENV` reads. Varlock ignores Vite's `envDir`; use `package.json`'s `varlock.loadPath` or CLI paths instead. ([Vite guide](https://varlock.dev/integrations/vite/), [pinned guide](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/integrations/vite.mdx), [plugin implementation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts).)

Core supports Bun and declares Node `>=22.3.0`. The Vite integration declares Node `>=22`, Vite `>=5`, and Varlock `^1.23.0` peers. These ranges do not certify Stack's Vite+ configuration. Upstream has explicitly fixed TanStack Router split-module replacement and Rolldown entry-detection issues, useful evidence of relevant maintenance rather than proof of this exact combination. ([Core manifest](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/package.json), [published integration manifest](https://registry.npmjs.org/@varlock/vite-integration/1.5.4), [integration changelog](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/CHANGELOG.md).)

Bun already loads dotenv files and exposes strings through `process.env`/`Bun.env`; it does not provide Varlock's schema/validation/secret-provider layer. Varlock recommends disabling native loading with top-level `env = false` in `bunfig.toml` or `--no-env-file`. Otherwise Bun-preloaded values become high-precedence process overrides, possibly defeating Varlock's environment selection. **Fit implication:** adopting Varlock changes ownership of dotenv loading; it is more than adding validation after native loading. Check both the Bun script launcher and `bunx --bun vp` path, since loading can occur before application code starts. ([Bun environment documentation](https://bun.com/docs/runtime/environment-variables), [Varlock Bun guide](https://varlock.dev/integrations/bun/), [pinned Bun guide](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/integrations/bun.mdx).)

For backend execution, upstream recommends `varlock run -- bun ...` so configuration exists before Bun starts, including for native SQL/S3/Redis clients that read startup environment. `import 'varlock/auto-load'` first enables typed `ENV` and runtime guardrails; when launched through `run`, it can reuse the injected graph. Loading only inside the process can be too late for native clients' implicit configuration. A global Bun preload is explicitly discouraged because of command coverage and initialization-order pitfalls. Elysia needs no dedicated integration package. ([Elysia guide](https://varlock.dev/integrations/elysia/), [pinned Elysia guide](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/integrations/elysia.mdx), [Bun guide](https://varlock.dev/integrations/bun/), [auto-load implementation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/auto-load.ts).)

The Vite integration's SSR injection modes do not initialize Stack's separately executed Elysia server. SSR is outside ADR 0002's scope. `resolved-env` can embed a complete secret-bearing graph into server artifacts, plaintext unless encryption is enabled; it should not be selected casually as a solution for the existing backend. Upstream also documents encrypted `freeze` files for deployments without a framework build, with key distribution and secret rotation tradeoffs. Neither mechanism is needed to evaluate basic validation and neither is selected here. Backend restart on schema changes under `bun --watch` and frontend/backend reload coordination remain unverified. ([Vite guide](https://varlock.dev/integrations/vite/), [encrypted deployments](https://varlock.dev/guides/encrypted-deployments/), [frozen env](https://varlock.dev/guides/frozen-env/).)

## Public exposure and logging safeguards

Sensitivity is independent of naming. Static non-sensitive `ENV.KEY` references can enter browser bundles without `VITE_`; sensitive items are dynamic by default and excluded from that ordinary static replacement path. `@public`/`@sensitive=false` therefore grant meaningful exposure permission, not just documentation. `import.meta.env` retains Vite's prefix-based replacement behavior. A sensitive value named `VITE_SECRET` must not be assumed safe merely because Varlock marks it sensitive; avoid conflicting channels and verify generated output. Public `@dynamic` values require runtime hydration; plain Vite users supply their own backend endpoint. This may matter for a single browser artifact deployed against different API origins. ([Vite guide](https://varlock.dev/integrations/vite/), [item decorators](https://varlock.dev/reference/item-decorators/), [pinned static replacement code](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts).)

Runtime protections patch console methods and HTTP response APIs. Elysia's standard `Response` path is documented as covered; a detected secret in a response body causes failure. These are guards against accidental exposure, not a sandbox: exact sensitive values are matched, transformed/encoded/truncated values are not generally recognized, and headers, cookies, WebSockets, files, and arbitrary sockets are outside body scanning. Performance and interactions with Elysia error/status logging need verification. The plain Vite plugin inspected here has no automatic output-scanning hook; broad documentation that integrations “usually” scan output does not establish that guarantee for this plugin. Explicit `varlock scan` can inspect build artifacts, including ignored files when requested. ([Secrets guide](https://varlock.dev/guides/secrets/), [pinned detailed scope](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/secrets.mdx), [plugin source](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts).)

Console redaction does not mutate the logged object. In-process stdout/stderr redaction requires `@redact={stdout=true}` in this release and skips interactive TTYs; `varlock run` redacts piped child output but also skips TTYs. Split writes, non-UTF-8 output, short values, and explicit opt-outs have documented limits; masking deliberately retains two characters. Crucially, **Stack's file drain is outside console/stdout redaction**: [logger setup](../../src/logger/elysia.ts) sends structured contexts into [the persistence drain](../../src/logger/persistence.ts), which calls `createFsDrain`. A redacted console line does not establish a sanitized JSONL file or custom drain. Do not log complete `ENV`, `process.env`, authorization values, or secret-bearing error contexts; any future claim of safe persisted logs needs a check at the drain boundary. No actual secret leak in the current application was demonstrated by this inspection. ([Pinned redaction scope](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/secrets.mdx).)

## CLI and secret-provider model

`varlock load` resolves and validates, returning nonzero on failure; `run -- command` validates before launching, injects variables plus a serialized graph by default, and propagates child status. `init`, `codegen`, `explain`, `scan`, encryption/reveal, caching, and freeze cover authoring and operations. **Machine output can expose secrets:** ordinary JSON, `json-full`, dotenv, and shell formats carry raw values. `--agent` redacts sensitive values for JSON inspection. Thus “the CLI redacts output” is not a guarantee for every format. ([CLI reference](https://varlock.dev/reference/cli/load-and-run/), [pinned CLI reference](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/reference/cli/load-and-run.mdx).)

Varlock can validate entirely platform-injected values without an external provider. Providers are optional plugins that add resolver functions, data types, and initialization decorators, for example `@plugin(@varlock/1password-plugin)` and `API_TOKEN=op(op://vault/item/field)`. Official integrations include password managers and cloud secret stores; authentication is provider-specific, so access still needs a bootstrap credential, local authenticated session, or workload identity. `@internal` can keep bootstrap values out of the child application environment. `exec()` is an escape hatch for custom resolvers, and bulk loading can map provider records to schema keys. ([Plugins guide](https://varlock.dev/guides/plugins/), [pinned plugin guide](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/plugins.mdx), [secrets guide](https://varlock.dev/guides/secrets/), [CLI reference](https://varlock.dev/reference/cli/load-and-run/).)

In JavaScript projects plugins must be installed dependencies; a decorator version can validate the installed range but does not override it. Standalone usage without `package.json` downloads and caches a fixed plugin version. This distinction matters for Stack's lockfile and dependency ownership. Provider selection, credential provisioning, offline startup, caching, and rotations remain application requirements; Varlock does not eliminate them. Core's empty regular dependency map also does not mean no implementation dependencies: bundled code and optional platform native helpers are part of its distribution. ([Pinned plugin installation rules](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock-website/src/content/docs/guides/plugins.mdx), [core manifest](https://registry.npmjs.org/varlock/1.23.0).)

## Fair comparison with T3 Env and simpler options

T3 Env's `@t3-oss/env-core` defines `createEnv({ server, client, clientPrefix, runtimeEnv })` in TypeScript and accepts Standard Schema validators, including Stack's existing Zod. It returns validated/transformed values and guards access to server variables from client code. It does not require global `process.env` type claims to pretend transformed values are strings. `emptyStringAsUndefined` is explicit, and boolean conversion comes from the validator; its recipes warn against naive boolean coercion. Bun/Vite loading stays application/toolchain-owned. These are substantial advantages when Stack needs validation without a separate configuration DSL or CLI. ([Core documentation](https://env.t3.gg/docs/core), [rationale](https://env.t3.gg/docs/introduction), [recipes](https://env.t3.gg/docs/recipes).)

T3 Env's scope is smaller: it validates the provided object, while Varlock additionally owns file resolution, provider loading, generated schema-derived types, and optional runtime redaction/leak guards. T3 Env's client-access proxy is not general secret-content scanning or log redaction. Its current source defaults validation failures to logging issues and throwing, supports custom error handlers, and permits `skipValidation`; values must still be kept out of logs and bundler definitions. Its docs warn that combined schema files can expose server variable names/descriptions and show separate schemas as an option. Neither library can make an explicitly public or manually inlined secret safe. ([T3 Env core guide](https://env.t3.gg/docs/core), [upstream core source, moving main](https://github.com/t3-oss/t3-env/blob/main/packages/core/src/index.ts).)

Bun's native loader already removes the need for a separate dotenv package in the backend. dotenv itself loads text values into `process.env`, while envalid's `cleanEnv` adds an immutable typed validation result with configurable reporting. Neither baseline needs Varlock's provider/schema lifecycle just to validate a port. They remain useful scope comparisons; no head-to-head runtime or bundle benchmark was performed. ([Bun docs](https://bun.com/docs/runtime/environment-variables), [dotenv upstream](https://github.com/motdotla/dotenv#readme), [envalid upstream](https://github.com/af/envalid#readme).)

## Decisions and evidence still needed

### Executed compatibility probe

After the design interview, the user authorized implementation. The initial feasibility probe ran against unpatched packages. The checked-in `scripts/probe-varlock.ts`, runnable with `bunx --bun vp run research:varlock`, has since become the patched contract probe. Against Bun, Vite+ 1.2.0 with `--configLoader runner`, Varlock 1.23.0, and Vite integration 1.5.4, it reproduced missing-value build failure, missing browser allowlist metadata for an ordinary HTML entry, and loss of public dynamic keys under static-only filtering once entry recognition is forced. A control with explicit entry recognition and a supplied dynamic value hydrates correctly and rejects an undeclared key. The emitted script is evaluated in happy-dom, not a real browser; all values are synthetic. See the [milestone gate result](../milestones/0004-varlock.md#reproduced-gate-result) for the exact scope and interpretation. The user then authorized targeted patches; the resulting Block and current qualification are documented in the milestone and environment guide.

### Interview follow-up: reusable artifacts and split configuration

The user accepted an optional Varlock Block with minimal abstraction, native schema-driven loading/validation/typed access/classification, and optional providers. Both browser and backend builds must work without deployment credentials, and the resulting artifacts must be reusable across deployments. These requirements are recorded in [ADR 0009](../adr/0009-resolve-deployment-configuration-at-runtime.md); the questions below are an initial research checklist, not a list of still-unanswered interview questions.

The monorepo guide is relevant even when browser and server share a package: schemas can live in explicit directories selected by `--path`/`loadPath`, and selective `@import(..., pick=[...])` can compose shared definitions. Separate package manifests are not a prerequisite for separate load roots. Per-project schemas and a shared tagged schema are both documented choices. Package-local generated `ENV` modules avoid merging browser/server declarations in a TypeScript program, but they still refer to the same runtime store within a process. ([Monorepo guide](https://varlock.dev/guides/monorepos/).)

Sensitivity and bundling time are separate axes. Public values default to static; public deployment-specific values need `@dynamic` to stay out of browser replacements. Dynamic means resolved at configuration load (typically server startup), not refreshed on every access. Upstream provides `getPublicDynamicEnv(keys?)` for server serialization and `loadPublicDynamicEnv({ endpoint })` or `setPublicDynamicEnv(values)` for browser hydration. Reads before hydration return `undefined`. Plain Vite requires an application-provided endpoint; boot-time injection is another documented option when the serving startup command is controlled. ([Dynamic configuration guide](https://varlock.dev/guides/dynamic-config/), [Vite integration](https://varlock.dev/integrations/vite/).)

Declaring a value dynamic alone is not evidence that loading/validation can succeed without it at build time. A compatibility spike must verify credential-free builds while retaining the browser's public-dynamic key metadata and generated types. Schema topology, public configuration delivery, and refresh semantics remain interview decisions.

Source inspection found a specific interaction to reproduce: a `!@dynamic` filter skips runtime-only validation, but it also removes excluded items from `json-full`. The Vite plugin derives its browser public-dynamic key allowlist from that returned graph, so filtering every dynamic key appears to prevent subsequent hydration. This is a source-level concern, not an executed reproduction; do not promise a blanket build filter as the solution. ([Filter implementation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/cli/helpers/item-filter.ts), [graph serialization](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/env-graph/lib/env-graph.ts), [Vite implementation](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts), [runtime hydration](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/runtime/env.ts).)

Further inspection qualifies the static-only build rule: filters resolve transitive value dependencies and values needed for computed decorators, so selecting a static item can still resolve a dynamic dependency. A genuinely credential-free build must keep its static values and selection metadata independent of runtime credentials. Upstream also permits `@sensitive @static`; static selection alone is therefore insufficient evidence of browser safety. Browser replacements should be restricted to public static values, with credentials remaining dynamic. `@defaultDynamic=inferFromSensitive` preserves sensitive/dynamic and public/static defaults; `@defaultDynamic=true` would make public values dynamic too. These observations inform the design interview; no dependency or bundler behavior has been reproduced locally. ([Scoped resolution](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/env-graph/lib/env-graph.ts#L1091), [Vite replacement construction](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts#L82), [root defaults](https://varlock.dev/reference/root-decorators/#defaultdynamic).)

Browser hydration rejects network/HTTP/JSON failures and non-object payloads, but does not itself validate per-key types or required-key completeness. Its key filtering depends on injected public-dynamic metadata; without that metadata, `setPublicDynamicEnv` accepts supplied keys. The returned payload is unfiltered even when the hydrated store is filtered. Likewise, server `getPublicDynamicEnv(keys?)` uses resolved metadata for classification, so endpoint registration must follow initialization rather than assume an arbitrary explicit key list is independently safe. Server validation, narrow serialization, metadata preservation, and bootstrap ordering therefore remain necessary integration checks. The endpoint owns its HTTP `Cache-Control: no-store` header. ([Runtime helpers](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/runtime/env.ts#L861), [Vite metadata injection](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/integrations/vite/src/index.ts#L841).)

The replacement matcher recognizes expression shapes such as `ENV.KEY`, rather than tracing imports to `varlock/env`. A Stack reexport or locally generated import named `ENV` is therefore plausible, but renamed bindings, computed/destructured access, and shadowed identifiers need deliberate verification. Preserve native access patterns rather than promising arbitrary syntax. ([AST replacer](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/utils/src/ast-replacer.ts).)

`@redact=false` disables CLI child-output redaction and skips fresh in-process console/stream patch installation. `@preventLeaks=false` separately skips fresh response wrapper installation. Existing wrappers are not necessarily undone in a reused process, and disabling interception does not eliminate configuration initialization overhead. ([Console installer](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/runtime/patch-console.ts#L16), [stream installer](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/runtime/patch-process-streams.ts#L260), [response installer](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/runtime/patch-response.ts).)

No native client-schema switch rejecting every sensitive item was found. A possible preflight uses the exported `internal.loadVarlockEnvGraph()` and composed item metadata; that is an explicitly internal API requiring exact-version ownership and tests. Metadata can itself depend on values, so rejecting sensitive declarations before any credential resolution also requires restrictions on value-dependent client classification. Filtering sensitive items out silently does not implement rejection. Local generated `ENV` modules only scope types and provide no runtime isolation. ([Internal API export](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/index.ts#L54), [metadata resolution](https://github.com/dmno-dev/varlock/blob/1b7fa9a4daa5eae432e6e3daa37a76cbb0089940/packages/varlock/src/env-graph/lib/config-item.ts#L998), [code generation guide](https://varlock.dev/guides/code-generation/).)

1. Is the requirement typed validation over Bun/Vite inputs, or configuration resolution plus secret providers and exposure guardrails? This determines whether Varlock's broader lifecycle earns its cost.
2. Should configuration be one app schema or independently scoped frontend/backend schemas? Decide which process can resolve which secrets and how public build values differ from runtime values. Package-local generated types may matter for multiple examples/apps.
3. Which native imports should Stack expose, and who owns provider dependencies? Verify Varlock module augmentation through any Stack reexport before promising the API. An opt-in block is consistent with ADR 0002; selecting exports or changing ADRs is outside this note.
4. Would the project accept Varlock ownership of dotenv loading and explicit startup wrappers? Resolve `APP_ENV`, Vite mode, and `NODE_ENV` policy, including tests and separate deployments.
5. What protection is required for persisted structured logs and custom drains? Console redaction is insufficient evidence. Decide whether any runtime patches are desired and test representative error/response/log paths before promising coverage.
6. In a later authorized spike, check the exact Vite+ config runner and TanStack splitting, missing/invalid/coerced values, type generation, direct and renamed imports, forbidden client access, conflicting `VITE_` secrets, public dynamic hydration if needed, Bun watch/restarts, and separate server startup. Inspect resulting browser assets and JSONL logs with synthetic secrets. These are proposed verification targets, not checks completed here.
