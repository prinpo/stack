# Vite+ with a project-local toolchain and Bun

Research date: 2026-11-05. Research only; no installation or configuration changes. Read the coding standards, domain guide, glossary, and ADRs 0003, 0004, and 0010 first. **Pinned** below means the installed `vite-plus@1.2.0`; **current** means the official online documentation and upstream `main` inspected today, not a claim about the latest published release. Upstream `main` currently declares `1.5.0`. ([Local manifest](../../node_modules/vite-plus/package.json), [upstream manifest](https://raw.githubusercontent.com/voidzero-dev/vite-plus/main/packages/cli/package.json).)

## Finding

**A global `vp` installation is unnecessary for this repository's project tooling.** Both pinned and current documentation explicitly allow local-only use: development/build/preview, checks/lint/format, Vitest, packing, tasks/cache, package-manager commands, creation/migration, and configuration. Keep the exact local package and matching Vite core alias; installing the global CLI would only add convenience and machine management. ([Pinned local-CLI guide](../../node_modules/vite-plus/docs/guide/local-cli.md), [current guide](https://viteplus.dev/guide/local-cli).)

**Bun as package manager and Bun as the CLI runtime are separate decisions.** Vite+ documents Bun installation, but its local-CLI guide still requires Node.js; 1.2.0 declares Node `^22.18.0 || ^24.11.0 || >=26.0.0` and uses `#!/usr/bin/env node`. Forcing Bun works in the probes below, and the CLI passes `process.execPath` to its native runner for JavaScript subprocesses. This supports the repository's chosen Bun execution approach, but is not proof of an upstream guarantee for every command without Node. ([Pinned manifest](../../node_modules/vite-plus/package.json), [launcher](../../node_modules/vite-plus/bin/vp), [native-runner invocation](../../node_modules/vite-plus/dist/bin.js), [current launcher](https://raw.githubusercontent.com/voidzero-dev/vite-plus/main/packages/cli/bin/vp).)

The repository already pins Vite+ and its core alias to 1.2.0 at root and in the example. ADR 0003 specifies `bunx --bun vp`; ADR 0010 requires delegated JavaScript tooling to run with Bun. Stack's CLI already resolves the application's installed Vite+ executable and launches it through Bun. Local-only use agrees with those decisions. Current and shipped installation guidance also recommends pinning Vitest to its bundled version when other dependencies import it; the local toolchain reports `5.0.4`. ([Root manifest](../../package.json), [example manifest](../../examples/fullstack/package.json), [ADR 0003](../adr/0003-vite-plus-and-bun-with-a-single-public-origin.md), [ADR 0010](../adr/0010-own-application-commands-through-the-stack-cli.md), [tool resolution](../../src/cli/tools.ts), [pinned installation guidance](../../node_modules/vite-plus/docs/guide/local-cli.md).)

## Global-only boundaries

These boundaries appear in the shipped 1.2.0 documentation as well as current guidance:

| Operation                                 | Local-only implication                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `vp env`, including `vp env doctor`       | Requires global CLI; supply/manage runtimes independently.                                                               |
| `vp upgrade`, `vp implode`                | Manage the global installation; update/remove local Vite+ with Bun instead.                                              |
| Vite+ global package operations with `-g` | Require global CLI; distinct from Bun's own global packages.                                                             |
| `vp list`, `vp rebuild` shortcuts         | Global only; local alternatives are `vp pm list` / `vp pm rebuild`, subject to the underlying package manager's support. |
| `vp toolchain --global`                   | Requires global CLI; use plain `vp toolchain` for the pinned local version.                                              |

Local `vp install` and other project package-manager commands **are supported**. When both CLIs exist, the global executable keeps package-manager/machine commands and delegates development commands to the local package; this dispatch rule does not mean local package management is unavailable. ([Pinned package-management guide](../../node_modules/vite-plus/docs/guide/package-management.md), [pinned local guide](../../node_modules/vite-plus/docs/guide/local-cli.md), [current package-management guide](https://viteplus.dev/guide/package-management), [current global selection rules](https://viteplus.dev/guide/global-cli#use-both-clis-together).)

## Resolution and bootstrap pitfalls

- **`bun vp …` resolves existing tooling; it does not bootstrap Vite+.** Bun resolves scripts/files before dependency binaries; `bun run` also permits system-command fallback. A future script named `vp` could therefore change the meaning. For an installed toolchain, prefer `bun --bun vp …`; the explicit root-relative `bun ./node_modules/vite-plus/bin/vp …` removes name-resolution ambiguity. ([Bun resolution order](https://bun.com/docs/runtime#resolution-order), [local binary declaration](../../node_modules/vite-plus/package.json).)
- **`bunx --bun vp …` uses the local executable when present, but has installation fallback.** If it cannot find that binary, the requested package name is `vp`, not `vite-plus`. `--bun` selects the runtime; it neither identifies the correct package nor pins its version. For intentional temporary bootstrap, name both: `bunx --bun --package vite-plus@1.2.0 vp …`. For installed-only execution, use `bunx --no-install --bun vp …` or the explicit local path. ([Bun executable/package selection and flags](https://bun.com/docs/pm/bunx), [pinned Vite+ bootstrap examples](../../node_modules/vite-plus/docs/guide/local-cli.md).)
- **Install dependencies before invoking a local binary.** Bootstrap this existing checkout through Bun, normally `bun install --frozen-lockfile`, rather than making local `vp install` a prerequisite for obtaining Vite+ itself. Include development dependencies. Vite+ package-manager detection recognizes this repo's `devEngines.packageManager` declaration of Bun 1.4.4. ([Repository manifest](../../package.json), [pinned detection rules](../../node_modules/vite-plus/docs/guide/package-management.md).)
- **Bun invocation alone does not override Node shebangs.** The current `prepare: "vp config"`, `check: "vp check"`, `test: "vp test"`, and Git hook `vp staged` resolve local binaries but retain the Node launcher. `bun --bun run check` / `bun --bun run test` force Bun for those script runs. A strictly Bun-only setup must explicitly address install-time `prepare` and hook execution too; changing only interactive instructions leaves those paths unresolved. The hook dispatcher adds local `.bin` to `PATH`, but does not select Bun. ([Bun runtime selection](https://bun.com/docs/runtime#--bun), [root scripts](../../package.json), [hook](../../.vite-hooks/pre-commit), [pinned dispatcher implementation](../../node_modules/vite-plus/dist/hooks-DhwsWb46.js).)

## Generated AGENTS block and `vp config`

The repository's marked block comes from Vite+'s shipped `AGENTS.md`; its description of a single global CLI is broader than the local-only guide. In 1.2.0, `vp config` reads that installed template and silently replaces the content between `<!--VITE PLUS START-->` and `<!--VITE PLUS END-->` in existing recognized, non-symlink agent files. It preserves surrounding text, skips unmarked files, and does not create missing agent files through this update function. Current upstream retains the marked-update mechanism. ([Pinned template](../../node_modules/vite-plus/AGENTS.md), [pinned updater](../../node_modules/vite-plus/dist/agent-KeDc6vmg.js), [current updater](https://raw.githubusercontent.com/voidzero-dev/vite-plus/main/packages/cli/src/utils/agent.ts).)

Because root `prepare` invokes `vp config`, editing only the generated block is not durable. Put repository-specific local/Bun instructions **outside the markers**, or deliberately adopt `vp config --no-agent` if the project wants to own the block. `--no-hooks` and `VP_GIT_HOOKS=0` skip hook setup, **not agent refresh**. Config also regenerates ignored hook dispatcher files and may set Git hook configuration; it does not regenerate `vite.config.ts`, project hook scripts, or staged configuration. ([Pinned config entry](../../node_modules/vite-plus/dist/config/bin.js), [current config entry](https://raw.githubusercontent.com/voidzero-dev/vite-plus/main/packages/cli/src/config/bin.ts), [official config/hook behavior](https://viteplus.dev/guide/commit-hooks#vp-config).)

## Verification and limits

On this machine, Bun reports 1.4.4 and `command -v vp` finds no global executable. Read-only probes succeeded for `bun vp toolchain vite`, `bun --bun vp --version`, `bunx --no-install --bun vp toolchain`, and explicit `--package vite-plus` local resolution. Reported versions: Vite+ 1.2.0, Vite 8.3.4, Rolldown 1.2.13, Vitest 5.0.4, Oxfmt 0.73.0, Oxlint 1.88.0. Local `env --help` and `toolchain --global` rejected global-only operations; `list --help` and `rebuild --help` were unknown commands, while `pm --help` listed both alternatives.

These probes establish local resolution, native binding loading, and metadata execution under Bun. Node is installed on the host; no clean Bun-only install or full check/test/build was performed. No `vp config`, install, migration, hook mutation, or global installation was run. The evidence supports local-only adoption now; complete Node-free compatibility remains a separate validation task.

The parent investigation additionally ran `bun install --frozen-lockfile`: it succeeded, invoked the existing `prepare: vp config`, and reported no dependency changes. `bun vp --version`, `bun vp toolchain`, and forced-Bun config/check/test help succeeded; `bun vp env doctor` returned the expected global-only error. These were setup and CLI probes, not full application validation.

## Recommended repository changes

Keep Bun and the pinned project-local Vite+ package; do not require a global `vp` installation. Use `bun install --frozen-lockfile` to bootstrap existing checkouts, and ordinary `bun install` when intentionally changing dependencies. Use `bun --bun vp <command>` for direct local tooling commands; `bun vp` also resolves the local executable, but the explicit flag selects Bun despite the Node shebang.

1. Replace the generated AGENTS block with repository-owned instructions. State that the absence of bare `vp` is expected; install with Bun when dependencies are absent or manifests/lockfile changed, and use the local executable afterward. Preserve the built-in/task distinction: root `bun run dev` starts Stack's example, whereas `bun --bun vp dev` starts Vite directly. Document local diagnostics (`bun --version`, `bun --bun vp --version`, `bun --bun vp toolchain`) instead of requiring `env doctor`, `--global`, or a global installation.
2. Change root `prepare` to `vp config --no-agent` and remove the template markers when replacing the block. This keeps hook setup while making agent guidance repository-owned; removing the markers also protects it from a later plain `vp config` refresh. Existing `check` and `test` scripts can retain bare `vp` because script execution adds local binaries to PATH.
3. Update root/example READMEs to bootstrap with Bun, then use the chosen local command spelling. Standardize executable examples in `.github/actions/check/action.yml`, root `example:check`, example `check`, and active guides such as `docs/eden-query.md` and `docs/env.md`. CI already bootstraps correctly in `.github/actions/setup/action.yml`. These existing post-install `bunx` commands work today; replacing them removes unnecessary installation fallback.
4. Reconcile ADR 0003's prescribed invocation with the new convention. Preserve historical test reports and third-party research command transcripts. Keep local Vite+ pins, the Vite alias/override, and Stack CLI tool resolution unchanged.

A fully Node-free workflow is a separate choice: explicitly run prepare/check/test/hook commands through Bun, including `.vite-hooks/pre-commit` and the staged command in `vite.config.ts`, then qualify installation, hooks, tests and builds without Node. A missing global `vp` alone does not require that broader change.
