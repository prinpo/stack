## 1. Connections, outages, and retries

### What upstream provides

`Queue`, `Worker`, `QueueEvents`, and `FlowProducer` need datastore connections. Workers need both a regular command connection and a dedicated blocking connection; `QueueEvents` also needs a dedicated connection for its blocking reads. Sharing a caller-owned client does not eliminate those duplicates. In the pinned backend factory, options-created connections and duplicates are owned, while shared caller clients remain caller-owned. Budget connections by queue, runtime instance, and application replica. See the [connections guide](https://docs.bullmq.io/guide/connections) and pinned evidence **P1–P3** below.

BullMQ 6.7.6 has an adapter interface, including Bun Redis support. It lazily loads optional ioredis only when no client factory/native client is supplied. Therefore, ioredis-centric examples are not universal connection semantics. The pinned Bun adapter owns reconnect scheduling and replaces raw clients through `duplicate()` after a disconnection; its delay calculation is `max(min(exp(attempts) * 100, 20000), 1000)` milliseconds. Its `options` getter returns an empty object and commands go through Bun's `send()`. Do not assume `maxRetriesPerRequest`, `enableOfflineQueue`, or a custom ioredis `retryStrategy` control this adapter merely because the native connection type accepts them. **P1, P3**; [adapter guidance](https://docs.bullmq.io/guide/connections).

The upstream distinction is intentional: request-facing producers should fail promptly during outages; background workers should reconnect and resume. With **ioredis**, use bounded request retries/offline queue policy for producers, and `maxRetriesPerRequest: null` for workers/blocking consumers. The [fail-fast pattern](https://docs.bullmq.io/patterns/failing-fast-when-redis-is-down) uses `enableOfflineQueue: false` and warns that initial connection availability is a separate concern. Native readiness is not an end-to-end request deadline. **P1, P3**.

Keep these mechanisms separate:

| Mechanism                        | What it controls                                       | What it does not establish                       |
| -------------------------------- | ------------------------------------------------------ | ------------------------------------------------ |
| Redis reconnect/request handling | Connection and command recovery                        | Whether an interrupted enqueue committed         |
| `attempts` and `backoff`         | Retrying handler failures                              | Producer request latency or crash-free execution |
| Stalled recovery                 | Work whose processing lock disappeared                 | Rollback of already performed side effects       |
| Stack producer/`run` timeout     | How long its caller waits, per the documented contract | Cancellation of a submitted command or handler   |

Native `attempts` describes total attempts, with one effective execution by default. Without backoff, eligible failures retry immediately. Built-ins are fixed and exponential backoff, with optional jitter; custom backoff can return `-1` to stop retrying. `UnrecoverableError` bypasses remaining attempts. `maxStartedAttempts` separately bounds starts, including paths that do not exhaust the ordinary failure budget. See [retry guidance](https://docs.bullmq.io/guide/retrying-failing-jobs) and **P4**.

### Implications for Stack

The documented defaults (`startupTimeoutMs: 10000`, `enqueueTimeoutMs: 5000`) are Stack guarantees, not BullMQ defaults. Keep bounds around validation, readiness, enqueueing, retrieval, and event readiness while preserving worker recovery. A timeout must not be described as proof of non-submission: an enqueue can commit before its acknowledgement reaches the producer. A late settlement also needs handling so it cannot create unhandled rejections or expose a closed runtime. These are implementation review targets, not observed Stack defects.

Document the Bun adapter's supported settings explicitly. Exercise startup with Redis unavailable, disconnect after readiness, unavailable blocking/event connections, recovery, and shutdown during reconnect. Retry the **business operation** using a stable identity; do not blindly create a new queue identity after every ambiguous timeout. This recommendation follows from the connection/timeout distinctions above and the [idempotent-job pattern](https://docs.bullmq.io/patterns/idempotent-jobs).

## 2. Production Redis durability and memory policy

BullMQ recommends Redis persistence, preferably AOF, and **`maxmemory-policy noeviction`**. Queue keys form a coordinated data structure; arbitrary cache-style eviction can remove part of that structure. The pinned client reads the policy from `INFO` and logs a warning if it is wrong; it does **not** configure Redis or fail startup on that warning. A successful ping/readiness check therefore does not establish production-safe configuration. [Production guide](https://docs.bullmq.io/guide/going-to-production); **P1**.

The pinned BullMQ version checks a generic minimum Redis version of 5.0.0 and recommends 6.2.0. Stack documents **Redis 7.2+ for its built-in Bun client**. These are different compatibility boundaries; the lower upstream check is not evidence for lowering Stack's qualified minimum. Compatible services such as Valkey require validation with the selected driver and topology. **P1**; Stack consumer documentation.

**Recommendation:** publish an application-owned production recipe covering persistence/fsync policy, durable volumes, recovery testing, `noeviction`, capacity alerts, and explicit retention. Separate cache workloads with eviction policies from jobs infrastructure. `noeviction` prevents arbitrary key loss but can cause writes to fail when memory is full; it does not supply unlimited capacity. AOF is a durability policy with a configured loss window, not an exactly-once execution guarantee. These are operational implications of the production guidance, not defaults Stack supplies.

## 3. At-least-once execution, stalls, and idempotency

BullMQ workers acquire and renew processing locks. Crashes, Redis interruptions, or a blocked event loop can prevent renewal. Another worker can recover that work, so a handler may execute again after its external side effect succeeded but before completion was recorded. Queue-level locking does not make an external API call or database write transactional with Redis. [Stalled jobs](https://docs.bullmq.io/guide/jobs/stalled), [worker concurrency](https://docs.bullmq.io/guide/workers/concurrency), [idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs); **P5**.

Pinned defaults are `lockDuration: 30000`, `lockRenewTime: lockDuration / 2`, `stalledInterval: 30000`, and `maxStalledCount: 1`. `stalledInterval` controls checking; it is not the lock-renewal setting. A stall is an event/recovery transition, not a permanent job state. Increasing `lockDuration` can accommodate pauses but delays crash detection; it does not provide an execution deadline. **P5**.

**Pinned nuance:** the Redis stall script requeues missing-lock jobs; for ordinary jobs exceeding the stall count, it stores a deferred failure that a worker finalizes. Jobs associated with an extant scheduler configuration are exempt from that script's `maxStalledCount` terminal-failure branch. Do not promise a universal hard execution-count bound from `maxStalledCount` alone. This is source evidence, more specific than the general stalled guide. **P5**.

**Recommendation:** teach idempotency at the side-effect boundary: unique business keys/database constraints, downstream API idempotency keys, resumable steps, or an application transaction/outbox when enqueueing must follow a database commit reliably. Use small handlers with explicit retry classification. A stable BullMQ `jobId` prevents some duplicate submissions while retained; it cannot prevent re-execution of that very same job after lock loss. Stack already documents repeated execution and unrecoverable input/name failures; keep that distinction prominent.

## 4. `run`, completion waiting, results, and retention

### Native completion observation

Pinned `Job.waitUntilFinished(queueEvents, ttl)` first awaits queue readiness, then installs listeners for `completed:<id>`/`failed:<id>` plus queue closure, starts an optional timer, waits for `QueueEvents` readiness, and checks stored terminal status **once**. This initial check closes the ordinary race where a job finished before listeners were installed. It is not continuous reconciliation polling. Its timer starts after the initial queue readiness await, and an omitted/zero TTL does not create a timer. See [Job API](https://docs.bullmq.io/api/classes/v6.Job.html#waitUntilFinished) and **P6**.

`QueueEvents` uses Redis Streams, parses result/progress JSON, tracks a cursor in its running loop, and by default begins at `$` (new events). The stream is approximately capped at 10,000 entries unless configured otherwise. It tolerates disconnects within retained history; a newly created listener does not automatically replay all previous events. Events are not a durable, acknowledged results inbox for each application consumer. [Events guide](https://docs.bullmq.io/guide/events); **P7**.

Consequences established by those source paths:

- A job already completed before observation can be resolved from stored state **if its job record still exists**.
- `removeOnComplete: true` or `removeOnFail: true` deletes the record at finalization. The status script reports a missing key as failure; there is a real race between an observed event and a missing-record status response. Immediate removal is therefore unsafe as a general completion-recovery policy, even though an already attached listener can receive the event's result.
- If the one-time check sees an unfinished job, the consumer disconnects, completion occurs, and that event is trimmed before reconnection, native waiting has no repeated state check to repair the missed event. A retained result can still be retrieved explicitly; native waiting can reach its TTL instead.
- The pinned native waiter uses an async Promise executor without a catch around its awaited event-readiness/status calls. **Source-derived review concern:** a rejection there is not wired to the outer rejection and can surface as an unhandled rejection while the outer wait lingers until TTL. This was not fault-injection tested; do not label it a demonstrated Stack defect. **P6–P7**.

Retries consume the caller's waiting budget. Queue delay, rate limiting, backlog, connection outages, handler time, and retry backoff all affect result latency. Stack documents a stricter required positive-integer `run.timeoutMs` covering the entire operation. Preserve that stronger bound independently of native `waitUntilFinished`, including cleanup on timeout and runtime shutdown. A timed-out `run` can subsequently finish successfully; timeout ends observation, not execution. Stack consumer documentation; **P4, P6**.

### Retention and result contracts

By default, completed and failed jobs are retained. Native policies allow immediate removal, a count, or `{ age, count }`; **age is in seconds**, unlike millisecond wait/backoff/TTL settings. Age/count cleanup is lazy at finalization, operates across job names within a queue's terminal set, and a count cap may remove a result before its intended age window. Removing a job also removes its ID-based submission barrier. [Auto-removal guide](https://docs.bullmq.io/guide/queues/auto-removal-of-jobs); **P8**.

Worker results are JSON-serialized. Date/class instances do not preserve runtime identity, and cyclic/BigInt results can fail serialization after application side effects ran. Stack deliberately defers mapping inferred result types to the JSON wire shape. Recommend JSON-native return shapes and store large/durable results in application storage, returning an identifier. Persist indispensable results inside the handler's durable business workflow, not solely in a `completed` event callback. An application-owned results queue is another upstream pattern, with its own idempotency/atomicity design. [Returning job data](https://docs.bullmq.io/guide/returning-job-data); **P6, P8**; ADR 0023.

**Recommendation:** make retention part of the `run` contract documentation. Retain terminal records long enough for completion reconciliation and expected disconnects, with capacity sized for the count cap. For stronger result reliability, consider periodic bounded terminal-state reconciliation in Stack's waiter or application-level durable operation records. Test instant completion/removal, failure removal, pre-existing completed IDs, Redis outages during waiting, event trimming, and serialization failure. These scenarios assess the declared contract without requiring a typed scheduler/flow API.

## 5. Job IDs and deduplication are different policies

Custom `jobId` uniqueness is **queue-wide**, not per job name. An existing retained ID suppresses insertion; removal allows reuse. Follow the documented rule to avoid `:` and numeric-only custom IDs. The pinned validator contains a compatibility exception for exactly three colon-separated segments; this is not a good application naming convention to adopt. It also rejects canonical integer strings. Prefer IDs such as `send-invoice-123`. [Job IDs](https://docs.bullmq.io/guide/jobs/job-ids); **P9**.

The pinned OSS package supports these deduplication options:

| Policy                               | Native options and behavior                                            | Limitation relevant to callers                                                                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Simple                               | `deduplication: { id }`; suppress while the existing job is unfinished | A subsequent submission can run after terminal finalization even while the old job record remains                                                   |
| Throttle                             | `{ id, ttl }`; suppress within a millisecond window                    | TTL is a dedup-key window, not a processing delay or job deadline                                                                                   |
| Debounce                             | Delayed job plus `{ id, ttl, extend: true, replace: true }`            | Replacement applies while delayed; it can remove/replace the previous record                                                                        |
| Reschedule                           | `{ id, reschedule: true }` with an incoming delay                      | Moves an existing delayed job's due time while retaining its ID/data/name/options; `replace` takes precedence                                       |
| Keep latest during active processing | `{ id, keepLastIfActive: true }`                                       | Stores the latest follow-up payload while active; creates it at terminal finalization; ordinary retries preserve the pending follow-up; ignores TTL |

These are **upstream OSS features already present in 6.7.6**, not proposed Stack helpers. See [deduplication guide](https://docs.bullmq.io/guide/jobs/deduplication), [API type](https://docs.bullmq.io/api/types/v6.DeduplicationOptions.html), and **P10**. Submission coalescing does not replace business idempotency after crashes. The keep-latest design prevents ordinary concurrent scheduling under a dedup ID; it cannot make a stale worker's external side effects stop after lock loss.

**Critical `run` implication:** native deduplication can return the **existing job's ID**, including for `keepLastIfActive` where a newer payload is merely reserved for later execution. Awaiting that ID means awaiting the existing operation, not necessarily the processing of the latest submitted input. Reusing a completed custom `jobId` can similarly return an earlier result. Stack documents checking stored kind/input when reusing work; that protects its declared type boundary but does not prove result/input equivalence for the new request. Document this policy, namespace IDs/dedup IDs by job kind/business operation, and let applications choose whether identical requests may share results. **P9–P10**; Stack consumer documentation.

## 6. Repeating jobs and Job Schedulers: v6 matters

BullMQ v6 removes `Queue.add(..., { repeat })`, repeatable-job getters/removers, `Repeat`, legacy `utc`, and the old `debounce` option. Public pinned `JobsOptions` excludes `repeat`; the internal scheduler-produced job type still includes it. Do not infer public repeat support from that internal type or from old guides. Use `queue.upsertJobScheduler(id, repeatOptions, template)` and scheduler getters/removal. Legacy persisted repeat metadata must be migrated while still on v5 before upgrading. [Migration guide](https://docs.bullmq.io/guide/migrations/migrate-from-v5-to-v6); **P11**.

Schedulers support interval/cron scheduling, timezone, start/end dates, limits, and templates with named jobs/data/options. Generated job IDs are scheduler-controlled. The next occurrence is produced when the prior occurrence begins processing: an overloaded/stopped queue can run less often than the nominal interval. This is not an audit log of every missed wall-clock tick. For interval schedules, the current repeat-options guide warns that new schedulers run their first repetition immediately; the older overview's “after one interval” description should not be treated as authoritative timing. Explicit future start dates and cron calculation need their own interpretation. [Scheduler guide](https://docs.bullmq.io/guide/job-schedulers/), [repeat options](https://docs.bullmq.io/guide/job-schedulers/repeat-options); **P11**.

**Stack boundary:** typed schedulers are deferred by ADR 0023. Applications can own native scheduler integration, preserving the registered job name/schema and runtime lifecycle. This does not justify promising a typed Stack scheduler today. Retain that deferral unless concrete application needs reopen it. A separate legacy `QueueScheduler` process is not required for modern BullMQ stalled/delayed processing. [Stalled guide](https://docs.bullmq.io/guide/jobs/stalled).

## 7. Flows and child-failure policies

Native `FlowProducer` creates dependency trees across queues on a shared backend. Parents normally wait until children succeed, then execute and can read child results through a job-keyed map. Flow creation groups queue inserts; it does not make handlers, external side effects, or compensations one transaction. In 6.7.6 unspecified flow IDs are UUIDs. [Flows guide](https://docs.bullmq.io/guide/flows/), [migration guide](https://docs.bullmq.io/guide/migrations/migrate-from-v5-to-v6); **P12**.

| Child option                | Pinned behavior after terminal child failure                                                                                           |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| None                        | Failed dependency remains unresolved; parent can remain `waiting-children`                                                             |
| `failParentOnFailure`       | Mark a deferred parent failure and make the parent eligible for worker processing; the parent worker finalizes an `UnrecoverableError` |
| `continueParentOnFailure`   | Release parent for processing before other dependencies finish; parent logic decides how to react                                      |
| `ignoreDependencyOnFailure` | Release this dependency, retain its failure detail, and wait for remaining dependencies                                                |
| `removeDependencyOnFailure` | Release this dependency and wait for remaining dependencies without recording it through the ignore-failure branch                     |

The four policies are mutually exclusive on a job. Options are set on the **child**. [Fail parent](https://docs.bullmq.io/guide/flows/fail-parent), [continue parent](https://docs.bullmq.io/guide/flows/continue-parent), [ignore dependency](https://docs.bullmq.io/guide/flows/ignore-dependency), [remove dependency](https://docs.bullmq.io/guide/flows/remove-dependency); **P12**.

Two documentation corrections matter: “immediate parent failure” still requires a parent worker, and “continue parent” makes it runnable rather than guaranteeing immediate active execution despite backlog/concurrency. Sibling work is not automatically cancelled. `removeUnprocessedChildren()` removes waiting/delayed children, not active work. Propagating failures through ancestors requires the relevant policy on each edge. **P5, P12**; the fail-parent guide's later lazy-failure note agrees with the source.

Pinned compatibility restrictions also matter: `Job.validateOptions` rejects deduplication combined with a parent; `FlowProducer` rejects deduplication on nodes with children. Do not assume all native feature combinations compose. **P9, P12**.

**Stack boundary:** ADR 0023 explicitly defers the typed flow API, while preserving future child-before-parent semantics, declared child kinds, job-keyed result unions, and default `failParentOnFailure`. That proposed default differs intentionally from upstream's default unresolved failure. Assess these as future design constraints, not existing Stack functionality. A future implementation needs failure cleanup/compensation and parent-worker availability documented, plus tests of policy combinations.

## 8. Rate limiting, concurrency, and CPU isolation

OSS local `worker.concurrency` controls one worker instance; multiple replicas increase aggregate capacity. Queue global concurrency (`setGlobalConcurrency`) limits the queue across workers. Queue-global rate limiting (`setGlobalRateLimit`) and worker-configured `limiter: { max, duration }` govern starts per window, not the number of active jobs or HTTP/API calls made inside a job. Long-running jobs can overlap; a single job can make multiple downstream calls. [Concurrency](https://docs.bullmq.io/guide/workers/concurrency), [global concurrency](https://docs.bullmq.io/guide/queues/global-concurrency), [global rate limit](https://docs.bullmq.io/guide/queues/global-rate-limit); **P13**.

The [rate-limit guide](https://docs.bullmq.io/guide/rate-limiting) describes a queue-wide shared limiter, manual `worker.rateLimit(duration)` with `Worker.RateLimitError()`, and TTL inspection. Its `groupKey` examples are explicitly pre-v3 and must not be copied into v6. Per-customer fair groups/group rate limits are [Pro groups](https://docs.bullmq.io/bullmq-pro/groups/), not implied by OSS queue limiting.

**Pinned source caveat:** when both worker and queue-global limiter settings are supplied, Redis activation selects global `max` first but selects worker `duration` first. This is narrower than the guide's broad statement that worker settings cannot override the global policy. Avoid conflicting configurations; validate mixed-policy behavior before depending on it. This is source-derived, not a benchmark or fault-injection result. **P13**.

High concurrency helps asynchronous I/O, not synchronous CPU-heavy JavaScript. Blocking the backend event loop also blocks HTTP handling and lock renewal. Native sandboxing requires a **processor file/URL**; child processes are the default, with `useWorkerThreads` as an option for file processors. Setting that flag on an inline callback does not move the callback to a thread. [Sandboxed processors](https://docs.bullmq.io/guide/workers/sandboxed-processors); **P5**.

**Stack boundary/recommendation:** native worker limiter/concurrency settings fit the documented queue `worker` pass-through. Inline handler definitions and the deferred separate-worker lifecycle do not by themselves provide sandboxing or workload isolation. Recommend modest measured concurrency for backend I/O jobs; keep CPU isolation as an explicit application-owned integration or future design item. Queue-global setters/manual worker APIs are upstream capabilities, not automatically methods on the typed Stack producer client.

## 9. Cancellation, deadlines, and shutdown

Pinned OSS BullMQ supports cooperative cancellation. A native processor can receive `(job, token, signal)`; `worker.cancelJob(id, reason)`/`cancelAllJobs()` abort signals on jobs tracked **by that worker instance**. The inline processor's declared arity must be at least three for the native worker to create the controller. Aborting does not interrupt arbitrary JavaScript, roll back side effects, or automatically choose terminal failure. Throw an ordinary error for configured retries or `UnrecoverableError` for permanent cancellation. Sandboxed processing forwards cancellation to its child signal, still requiring cooperation. [Cancellation guide](https://docs.bullmq.io/guide/workers/cancelling-jobs); **P5, P14**.

Do not confuse three clocks: caller `run.timeoutMs`, a handler's per-attempt processing timeout, and a business deadline including queueing and retries. Native public job options do not supply a general execution timeout. Upstream demonstrates a handler timer plus abortable I/O and deliberate error classification; `delay` is only scheduling eligibility. For an end-to-end deadline, carry an absolute deadline in validated data and check it on each attempt before effects. Timer-based cancellation cannot preempt a synchronous blocked loop. [Timeout pattern](https://docs.bullmq.io/patterns/timeout-jobs), [sandbox timeout pattern](https://docs.bullmq.io/patterns/timeout-for-sandboxed-processors); **P8, P14**.

Cross-process cancellation is application coordination. Current upstream supplies an OSS [Relay cancellation example](https://docs.bullmq.io/guide/relay/examples/cancelling-jobs-on-other-workers); Relay is exported in the installed package. It distributes requests to workers that call their local cancellation method. A publish-delivered result is not proof that the owning worker cancelled a running handler. A durable user-visible cancellation/deadline requirement still needs recorded intent and handler checks, especially for queued jobs. Stack documents no such typed cancellation/Relay integration today. Do not misclassify all cancellation as Pro-only: [Pro observable TTL cancellation](https://docs.bullmq.io/bullmq-pro/observables/cancelation) is a distinct feature.

Native `worker.close()` waits for active processing with no intrinsic grace deadline; `close(true)` skips waiting. Stack documents its own `JOBS_SHUTDOWN_TIMEOUT_MS`, abort on grace expiry, and force-closing owned resources. Preserve that bounded lifecycle and require cooperative handlers. Runtime/source reload interruption can still lead to stalled recovery, so shutdown is another reason for idempotency. Force-closing Redis is not evidence that inline application work stopped. **P5, P14**; Stack consumer documentation.

## 10. Events, metrics, telemetry, and OSS versus Pro

| Capability                                                                            | Upstream availability                                | Stack assessment boundary                                                               |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Queue/worker EventEmitter events and Redis Stream `QueueEvents`                       | OSS                                                  | Completion waiting needs these semantics; browser subscriptions are deferred            |
| Minute-bucket completed/failed counters via worker `metrics` and `Queue.getMetrics()` | OSS, opt-in                                          | Native worker metrics settings fit pass-through; no documented Stack monitoring service |
| `Queue.exportPrometheusMetrics()`                                                     | OSS                                                  | Application supplies scrape endpoint and monitoring configuration                       |
| Telemetry interface with tracing/context propagation and optional meter               | OSS                                                  | Queue and worker options can accept instrumentation; integration is application-owned   |
| `bullmq-otel` implementation                                                          | Separate optional integration, not a Pro requirement | Not declared in Stack's package dependencies; v6-compatible implementation needed       |
| Queue-wide rate limit/global concurrency/schedulers/flows/native cancellation         | OSS                                                  | Native availability does not imply typed Stack helpers                                  |
| Fair groups, group-level policy, observable processing/TTL, worker batch processing   | Pro commercial package                               | Not supplied by Stack's pinned `bullmq` package                                         |
| Bulk enqueue and bulk flow creation                                                   | OSS                                                  | Different from Pro processing batches; typed Stack bulk helpers remain deferred         |

Sources: [events](https://docs.bullmq.io/guide/events), [metrics](https://docs.bullmq.io/guide/metrics), [Prometheus](https://docs.bullmq.io/guide/metrics/prometheus), [telemetry](https://docs.bullmq.io/guide/telemetry/), [OpenTelemetry setup](https://docs.bullmq.io/guide/telemetry/getting-started), [batch distinctions](https://docs.bullmq.io/guide/queues/batches), [Pro introduction](https://docs.bullmq.io/bullmq-pro/introduction); **P7, P15**.

Minute metrics need consistent `maxDataPoints` across workers. They are throughput history, not a per-job latency/error audit. The pinned Prometheus exporter includes current state gauges **and** completed/failed total counters read from native metrics metadata; without enabling collection, totals do not establish actual lifetime throughput. Telemetry is separate from Redis minute buckets. In v6 a supplied meter must implement `createGauge`; `bullmq-otel >=2.0.0` is an optional peer. **P15**; [migration notes](https://docs.bullmq.io/guide/migrations/migrate-from-v5-to-v6).

**Recommendation:** add application monitoring for connection errors, terminal failures, retry pressure, stalls/lock-renewal failures, waiting age/backlog, and shutdown duration. Local worker `failed` events can occur on retryable attempts; distinguish them from terminal `QueueEvents` failures. Stack's documented `onError` covers infrastructure errors, not ordinary handler failures. Include business/job identity in logs without putting sensitive payload/result values into logs or telemetry by default: the pinned completion span explicitly attaches the serialized result. No built-in Stack dashboard, alerting, or Pro functionality should be inferred from native exports. **P4–P7, P15**.

## Assessment priorities for the parent review

1. **Verify the promised lifecycle bounds with the actual Bun adapter.** Include readiness of blocking/events paths, recovery, late producer settlements, and owned versus caller-owned cleanup.
2. **Review `run` as an observation contract.** Resolve removal races, missed/trimmed events, timeouts, and listener cleanup; document how reused IDs/deduplication share existing results.
3. **Publish production Redis and idempotency requirements.** Readiness alone cannot establish persistence, `noeviction`, business deduplication, or durable results.
4. **Keep policy application-owned with sound examples.** Use bounded retry/backoff/jitter and retention appropriate to the workload; distinguish attempts, stalls, rate limits, and deadlines.
5. **Respect ADR 0023's deferred scope.** Native scheduler/flow/Relay/sandboxing capabilities are useful escape hatches and future design inputs, not evidence that the typed Jobs Block already supports them.
6. **Describe observability accurately.** OSS events, metrics, Prometheus, and telemetry are available; installing/configuring them and providing alerts remains separate work. Pro groups/observables/batch processing are a different package.

These recommendations follow from the cited behavior. No implementation bug, runtime compatibility guarantee, performance number, or new product commitment is asserted without the parent's separate implementation review.
