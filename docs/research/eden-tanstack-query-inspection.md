## Assessment for Stack

The upstream adapter is a useful reference and a possible source for **explicitly attributed adaptation**. It fits Stack's preference for native TanStack Query options and hooks. Its difficult part is reconstructing route/request/response types and keeping cache identity consistent with actual requests, rather than introducing another HTTP client. The tests and changelog are especially valuable guides to that contract. Owning this source would give Stack control over fixes, while also transferring responsibility for these compatibility rules to Stack.

Provisional recommendation: first decide whether Stack needs the route-mirroring API (`eden.users.get.queryOptions()`). If it does, evaluate adapting a coherent subset of the upstream adapter and its regression tests with visible credit. If it does not, evaluate a smaller bridge around native Treaty calls and Query options, with application-defined keys. A complete copy with a renamed factory would retain almost all upstream maintenance responsibilities. No source has been incorporated into Stack by this inspection.

## Ownership choices to evaluate

These are implications for discussion, not a selected architecture:

- **Pin the upstream package:** Stack can own the version it ships and the tests qualifying that version, while upstream owns the adapter implementation. Local fixes would still need a patch, fork, or upstream release. This is the least source maintenance, but does not itself provide implementation independence.
- **Maintain an attributed adaptation:** Stack can own release timing and selected implementation code while naming its upstream origin and retaining the applicable Apache notices. The maintained surface includes every copied runtime/type helper and its regression tests. Adaptation should record a baseline commit and changes so future upstream fixes can be assessed deliberately.
- **Use a small native integration:** Stack can build a narrower public surface using Eden calls and TanStack Query's own options APIs. This reduces the surface only if required behavior is narrower; typed route proxies, automatic keys, pagination, error semantics, and inference still require design and tests wherever Stack chooses to provide them. If upstream code is copied during that work, it remains an attributed adaptation regardless of the new package name.

Stack's existing ADRs already call for exact integrated dependency pins, tested upgrades, native library concepts, and justified abstractions. Choosing among these approaches needs the behavior/architecture inspection and Stack's intended API scope; maintenance history alone cannot select one. ([Dependency ownership ADR](../adr/0001-stack-owns-library-dependencies.md), [native APIs and independent Blocks ADR](../adr/0002-compose-independent-blocks-with-native-apis.md).)

## Architecture and the work Stack would inherit

The package has 12 source files, about 3,800 lines including comments and examples. Two type modules alone account for 1,663 lines; this is a rough size indicator, not a count of executable logic. The browser build externalizes its major integrations; Elysia and Treaty references in the adapter's implementation are type imports. It delegates requests to an existing Treaty client. ([Source tree](https://github.com/xkelxmc/eden-tanstack-query/tree/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src), [build configuration](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/package.json).)

The implementation has four layers:

1. **Route types.** `types/infer.ts` reads Elysia's `~Routes` and normalizes inputs, successful status codes, errors, bodyless responses, forms, and generators. `types/decorators.ts` builds the callable route tree and Query option overloads, including optional paths, selected data, initial data, and data-tagged cache keys. Recreating this interface means maintaining a second interpretation of Elysia/Treaty's types. ([Inference](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/types/infer.ts), [decorators](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/types/decorators.ts).)
2. **Runtime route proxy.** `createOptionsProxy.ts` records static segments and the positions of dynamic parameter calls. It replays those calls against Treaty, maps GET/HEAD/OPTIONS to queries and POST/PUT/PATCH/DELETE to mutations, parses request inputs, and unwraps `{ data, error }` into resolved data or a thrown error. It also generates keys and filters. This is the main runtime coordination module, at 730 source lines including comments. ([Proxy](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/proxy/createOptionsProxy.ts).)
3. **Keys and option factories.** Keys contain route segments, input, ordered path parameters, query kind, and infinite-query initial cursor where applicable. Ordinary and infinite data need distinct identities. Low-level option factories supply the fetch/mutation functions while preserving TanStack options and type tags. These can be studied separately from the route proxy, but consistent key generation, request routing, and filtering form one behavioral contract. ([Keys](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/keys/queryKey.ts), [ordinary options](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/options/queryOptions.ts), [infinite options](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/options/infiniteQueryOptions.ts), [mutation options](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/options/mutationOptions.ts).)
4. **Optional React access.** `createEdenTanStackQuery()` delegates to the context factory, which exposes a memoized proxy and the raw Treaty client through hooks. The adapter does not replace Query's hooks or own its cache. A standalone proxy can be created outside React, useful for Router loaders and prefetching. The deprecated `queryClient` factory/provider argument is unused. ([Context](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/context.tsx), [factory](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/createEdenTanStackQuery.ts), [proxy](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/proxy/createOptionsProxy.ts).)

For Stack, keep any React Query integration behind an opt-in Block entry point. Reexporting the upstream package from the existing Eden-only `@prinpo/stack/client` entry point would introduce React/React Query runtime imports there. Preserve raw Treaty access, native Query hooks, and standalone options for Router loaders. QueryClient/provider composition also needs an explicit pattern: Stack's current `createRootAndRender()` only renders RouterProvider. This is future implementation work, not a reason to make Query mandatory for Router or Eden consumers. ([Stack client](../../src/client.ts), [Stack React entry point](../../src/react.tsx), [independent Blocks ADR](../adr/0002-compose-independent-blocks-with-native-apis.md), [upstream exports](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/index.ts).)

## Behavioral limits and choices to make deliberately

These are observed contracts or documented limitations, not newly confirmed defects:

- **Cache scope.** Keys omit backend URL and Eden context. Upstream explicitly documents collisions when two backends with identical routes/inputs share one QueryClient and recommends separate QueryClients. Authentication supplied through cookies or client-level headers likewise does not become a key automatically. Stack needs a documented cache lifecycle for session changes; a namespace would be an additional design choice. ([Multiple API instances](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/apps/docs/content/docs/api-reference/create-eden-tanstack-query.mdx), [key implementation](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/keys/queryKey.ts).)
- **Input reshaping.** Ordinary queries accept direct query fields or wrappers with an explicit `headers` property. Names such as `query` and `headers` require special disambiguation. Mutation variables are body-only by default, with an explicit `request: true` mode for `{ body, query, headers }`. These conveniences create rules beyond native Treaty and account for multiple recent fixes. ([Proxy parsing](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/proxy/createOptionsProxy.ts), [0.5.0/0.4.0 changes](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/CHANGELOG.md).)
- **Reserved route names.** Procedure helper/schema names are reserved after method-named path segments. For example, the native Treaty route `/api/get/headers` is covered by an upstream test, while the adapter hides the `headers` child at that location. Raw Treaty remains an escape hatch. ([Reserved members and procedure proxy](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/proxy/createOptionsProxy.ts), [real Treaty reserved-path test](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/test/integration/realTreaty.test.ts).)
- **Cancellation.** Query signals reach Treaty only when `eden.abortOnUnmount` is enabled. That setting also controls forwarding for explicit QueryClient cancellation, despite its name. With forwarding disabled, an existing Treaty-configured signal is preserved. Stack should choose and document the intended behavior. ([Options factory](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/options/queryOptions.ts), [cancellation tests](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/test/integration/realTreaty.test.ts).)
- **Pagination convention.** Infinite-query helpers assume a supported top-level `cursor` field; required cursors need an explicit initial cursor, and union query schemas do not expose these helpers. This is a particular pagination convention, not universal pagination support. ([Cursor and overload types](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/types/decorators.ts), [package documentation](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/README.md).)
- **Typed compatibility is part of versioning.** TanStack explicitly recommends patch-version pins because type changes can ship in patches. Stack's existing exact-version policy fits that advice. Runtime test success alone does not verify selected-data inference, required inputs, error unions, or cache write types. ([TanStack TypeScript guidance](https://tanstack.com/query/latest/docs/framework/react/typescript), [Stack ADR](../adr/0001-stack-owns-library-dependencies.md).)

The existing skip-token regression tests also check interaction with a global default query function and an enabled observer sharing the same key. Any adaptation should preserve this behavior rather than mechanically replacing the upstream implementation with a different skip-token shape. ([Observer regression tests](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/test/proxy/createOptionsProxy.test.ts).)

## Suggested reuse boundary for the next discussion

The most valuable material is the **behavioral contract and regression cases**: real Treaty request invocation, throwing Eden errors for Query, dynamic-path cache identity, ordinary/infinite key separation, tagged cache reads/writes, required-input enforcement, and selected/initial-data inference. If code or test fixtures are carried over, record their provenance and preserve their licenses and attribution.

The route proxy, key scheme, route-type decorators, and option overloads are coupled. Selecting only the proxy while discarding its key or type rules would require redesign and fresh verification. Conversely, the React context is small and separable; it need not define the core integration or become a prerequisite for loader usage. General-purpose utility exports, deprecated arguments, SSR examples, and every pagination/input convenience need not become Stack's public API merely because upstream exposes them. ([Proxy](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/proxy/createOptionsProxy.ts), [decorators](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/types/decorators.ts), [public exports](https://github.com/xkelxmc/eden-tanstack-query/blob/69ad5d0e0fcf489f7a3daac31c12a63de8b250af/packages/eden-tanstack-query/src/index.ts).)

A narrower bridge would instead keep native Treaty calls visible, infer results from those calls, and let native `queryOptions`/`mutationOptions` carry Query types. It would trade automatic route-derived keys and proxy ergonomics for less duplicated route inference and more application-owned query definitions. This is an alternative to evaluate, not an implementation completed here. ([Native options inference](https://tanstack.com/query/latest/docs/framework/react/typescript).)

For either direction, Stack should eventually qualify each release with runtime tests against real Treaty, compile-time positive/negative fixtures, and the exact supported dependency set. Upstream's tests provide a strong starting inventory. The next decision is which developer experience and capabilities Stack promises to maintain; no ADR, dependency installation into Stack, or implementation has been made by this inspection.
