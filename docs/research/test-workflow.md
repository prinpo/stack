## Dependencies outside the Vitest import graph

Stack starts some tests at the same entry points a consumer uses. A test starts Bun, the Stack CLI, a Vite build, or a package consumer, and that process loads its own code and files. The parent Vitest process sees the test module's imports. Its graph misses subprocess arguments, imports inside strings written to fixtures or sent to `bun --eval`, computed module paths, and arbitrary file reads unless the file is also registered with Vite. A suite can therefore appear in an affected run for one dependency and disappear for another. Type-only imports are erased, and `vp check` supplies the separate type-check signal.

The Compose test now has a commented side-effect import of `src/cli/compose.ts` to give Vitest a graph edge to the implementation it exercises through the CLI. The import is a discovery hint. The assertions run against the separate CLI process. After the change, `vp test related --run src/cli/compose.ts -t 'explicit Compose commands target'` selected the Compose suite and passed both matching cases. Keep this technique limited to specific modules that are safe to evaluate in the test process. For example, importing `src/cli/main.ts` evaluates the command dispatcher, and importing `src/browser-log/built.ts` initializes built-mode logging. Select those suites explicitly. [Compose test](../../tests/cli-compose.test.ts), [CLI entry point](../../src/cli/main.ts), [built browser log entry point](../../src/browser-log/built.ts), [Vitest graph implementation](https://github.com/vitest-dev/vitest/blob/6a11cf66f99fa610b7364363d5ca42b66d994f40/packages/vitest/src/node/affected-modules.ts)

### Adopted workflow

- **Edit loop.** Run a known test file with `bun --bun vp test run <file>` and add `-t '<name>'` to filter to a case. Run `bun run test` before local handoff. It runs the `stack`, `i18n-browser`, and `eden-query` projects with eight workers. Use `bun run test:integration` and `bun run test:smoke` for the heavier groups. This follows T3 Code's focused-test guidance. [Stack agent instructions](../../AGENTS.md#local-tests), [T3 Code agent guidance](https://github.com/pingdotgg/t3code/blob/8213d1dda2070544694e53cff1a16783279e2122/AGENTS.md#L78-L84)
- **Branch check.** `bun run test:changed [base]` combines native Vitest selections with explicit suites for subprocess and fixture inputs. It prints the chosen files and falls back to all projects for shared or unclassified inputs or discovery errors. It uses the Git merge base (default ref `origin/main`) plus staged, unstaged, and untracked files. Changes confined to known reference docs select zero tests. Packaged docs are smoke inputs. T3 Code uses colocated tests and explicit exceptions locally. Stack's central `tests/` layout calls for a path map. [Stack selector](../../scripts/test-changed.ts), [T3 Code local selector](https://github.com/pingdotgg/t3code/blob/8213d1dda2070544694e53cff1a16783279e2122/scripts/check-changed.ts#L329-L347)
- **CI.** Run all test projects in one invocation for PRs, merge groups, and main. Release preparation also validates the exact tarball it publishes. T3 Code selects affected workspaces and transitive dependents for PRs, then runs a full main-branch check. Stack's CLI, environment, example, and package tests share inputs across one library, and its runner executes one job at a time. The main saving comes from making the frequent local path smaller. The Compose timeout test also drops its fixed wait by advancing the timer in the CLI subprocess while exercising real signal delivery. [Stack CI](../../.github/actions/check/action.yml), [Stack runner](../self-hosted-runner.md), [T3 Code CI selection](https://github.com/pingdotgg/t3code/blob/8213d1dda2070544694e53cff1a16783279e2122/.github/scripts/ci-changes.cjs)

The implemented fast projects passed 673 tests across 59 files in 6.73 s at four workers and 3.98 s at eight workers in sequential runs. All 69 existing files were discovered exactly once. Running all projects passed 855 tests. The standalone integration and smoke commands passed 181 and 1 test respectively. The eight-second target is an informal benchmark.

Use the pinned Vitest runner now. Bun's native `--changed` uses Bun's own test runner. A direct `bun test ./tests/server.test.ts` probe passed 10 tests and failed five because Bun 1.4.5 lacks the `toHaveBeenCalledExactlyOnceWith` matcher used by this file. Vite+ passed all 15. A migration would also need to qualify project configuration, environment, setup, module mocks, and discovery. [Server regression cases](../../tests/server.test.ts#L154) Vitest 5.1 adds the experimental `--since-last-run` for recurring local runs, and the installed toolchain exposes Vitest 5.0.4. Consider the new option on a normal Vite+ upgrade. Its module records still cannot describe arbitrary subprocess inputs. None of those upgrades is needed to get faster feedback today. [Bun 1.4 test changes](https://bun.com/blog/bun-v1.4), [Vitest 5.1](https://vitest.dev/blog/vitest-5-1)

Keep full execution in CI before introducing path gates, sharding, generic task caching, or a custom test dependency graph. Those options are worth revisiting if CI starts to dominate lead time after removing the fixed wall-clock wait. Shared fixtures, toolchain cache changes, and retry tuning should each earn their complexity through a separate measurement.

The server uses eight duration-weighted shards through `vp run test:cached -- --shard <index>/8 --concurrency 4 --uncached apps/server/integration/transferBudgetV2.integration.test.ts --verify-hits 1 apps/server`. Its wrapper schedules individual files as cacheable tasks using automatic inputs, with an explicit report-producing test always executed and a sampled cache hit rerun without cache. These jobs rely on package gating, sharding, and caching for throughput. They do not invoke Vitest's changed-file flag or collect a code coverage report in the cited test steps. T3 Code's catalog pins Vite+ 1.8.0. ### Bun, Vitest, and Vite+ selection

| Goal                                   | Command                                                                            | Selection                                                                                                          |
| -------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Native Bun tests for local edits       | `bun test --changed`                                                               | Staged, unstaged, and non-ignored untracked files, then related Bun test files.                                    |
| Native Bun tests from a known base     | `bun test --changed=<ref>`                                                         | Working-tree diff directly against the ref, plus non-ignored untracked files.                                      |
| Vitest tests for local edits           | `vitest run --changed`                                                             | Staged, unstaged, and non-ignored untracked files in the pinned 5.0.4 implementation.                              |
| Vitest tests for a branch              | `vitest run --changed=origin/main`                                                 | Committed changes since the merge base with the named ref, plus staged, unstaged, and non-ignored untracked files. |
| Vitest tests for explicit source paths | `vitest related --run src/file.ts`                                                 | Test files that reach the given source path, using the same selection machinery as `--changed`.                    |
| Stack's pinned Vitest runner           | `bun --bun vp test run --changed` or `bun --bun vp test run --changed=origin/main` | Same Git selection through Vite+ and the configured Stack test projects.                                           |
| Direct Stack test selection            | `bun --bun vp test run tests/file.test.ts -t 'pattern'`                            | Positional path filter and test-name regex. Use `--project eden-query` for a configured project.                   |
| Inspect Stack's candidate files        | `bun --bun vp test list --filesOnly --changed`                                     | Report candidate files through Vitest's collection path, which uses the same source filter.                        |

- **Bun's graph.** The feature shipped in 1.3.13. On 1.4.4, Bun scans transitive imports from discovered test entry points without executing tests, skips dependencies resolved as packages under `node_modules`, and supports TypeScript path aliases. Unresolved/import-invisible dependencies can escape selection. The graph alone cannot establish the impact of fixtures read at runtime, subprocesses, environment changes, or package/config changes that have no graph edge. Empty affected sets succeed; Git errors fail; a whole-graph construction error falls back to all discovered tests. With `bun test --changed --watch`, the first run uses Git. The pinned implementation uses watcher-trigger paths for subsequent restarts on POSIX when available, so a second edit can rerun only its own tests even when the first file is still dirty. Windows falls back to Git. This is more specific than the launch announcement's description of re-querying Git on every restart. [Bun 1.4 overview](https://bun.com/blog/bun-v1.4), [1.4.4 graph and watch implementation](https://github.com/oven-sh/bun/blob/38afee6c84fcf48c0edb2466aa4b27d287a59c30/src/runtime/cli/test/ChangedFilesFilter.rs#L65-L188), [1.4.4 selection tests](https://github.com/oven-sh/bun/blob/38afee6c84fcf48c0edb2466aa4b27d287a59c30/test/cli/test/test-changed.test.ts).
- **Vitest's graph.** Static selection transforms modules to build a graph per Vite project. It follows static imports, including literal dynamic imports, and can see files a Vite plugin registers through `addWatchFile`. Arbitrary computed imports, filesystem reads and subprocesses need separate coverage. The runner knows about setup and global setup, project configuration dependencies, env files loaded through `envDir`, and standard snapshots, with documented exceptions such as `toMatchFileSnapshot`. The default `forceRerunTriggers` covers `**/package.json` and `**/{vitest,vite}.config.*`; add project-specific inputs only where this safety net is needed. An empty changed selection can pass because `changed` defaults `passWithNoTests` to true. With `--coverage`, the changed report covers only files related to the changes. [Changed config](https://vitest.dev/config/changed), [Vitest 5.0.4 graph](https://github.com/vitest-dev/vitest/blob/6a11cf66f99fa610b7364363d5ca42b66d994f40/packages/vitest/src/node/affected-modules.ts), [default triggers](https://github.com/vitest-dev/vitest/blob/6a11cf66f99fa610b7364363d5ca42b66d994f40/packages/vitest/src/defaults.ts#L101-L108), [empty-selection default](https://github.com/vitest-dev/vitest/blob/6a11cf66f99fa610b7364363d5ca42b66d994f40/packages/vitest/src/node/config/resolveConfig.ts#L803-L811).
- **Version and tool boundaries.** Stack pins Vite+ 1.2.0 with Vitest 5.0.4. The current Vite+ guide lists Vitest 5.1.1. Vitest's `--since-last-run` arrives in 5.1.0 and requires a cached baseline. It starts with a full run, then uses mtimes and prior loaded-file records, including exercised dynamic imports. Older mtimes and newly discovered dependencies can escape that comparison. The opt-in `experimental.recordDependencies` exists in 5.0.4 and can also accelerate `--changed` after priming, with stale-record, filesystem-read, and externalized-module limits. Vite+'s `vp test` resolves its bundled Vitest first and defaults to a one-shot run. `vp run test` invokes a configured script or task, and `vp run --filter <package> test` filters at workspace scope. `bun test` invokes Bun's native runner with its own discovery and execution semantics. [Stack lockfile](../../bun.lock), [pinned Vite+ guide](https://github.com/voidzero-dev/vite-plus/blob/882872042ce1a3424a82b976641bbe9099634d9b/docs/guide/test.md), [current Vite+ guide](https://viteplus.dev/guide/test), [Vite+ workspace filters](https://viteplus.dev/guide/run#filter---filter), [Vitest affected-tests recipe](https://vitest.dev/guide/recipes/affected-tests), [Vitest 5.0.4 dependency recording](https://github.com/vitest-dev/vitest/blob/6a11cf66f99fa610b7364363d5ca42b66d994f40/docs/config/experimental.md#L379-L419).

- **Coverage on selected tests.** Bun's `--coverage` reports executed code, with text and LCOV reporters and default exclusions for test files, dependencies, and files loaded by non-JS/TS loaders. A report from a selected run describes that run. Vitest offers V8 and Istanbul providers via separate packages, and by default reports files imported during testing unless `coverage.include` adds uncovered files. Vitest's extra exclusions for changed runs make selected-run percentages a poor substitute for a full-run threshold. [Bun coverage guide](https://bun.com/docs/test/code-coverage), [Vitest coverage guide](https://vitest.dev/guide/coverage), [Vitest changed config](https://vitest.dev/config/changed).
